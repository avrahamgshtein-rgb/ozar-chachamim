# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout — read this first

This repo contains **two generations of the same project**. Only one is live:

- **`nextjs-app/`** — the active, deployed app (Next.js 15 + React 19). `.github/workflows/deploy.yml` builds and deploys *this* directory to Vercel on every push to `main`. All feature work happens here.
- **Repo root** (everything outside `nextjs-app/`) — a legacy vanilla-JS/Supabase prototype (`index.html`, `graph.js`, `styles-graph.css`, dozens of one-off `*.md` status reports, migration scripts, scratch JSON exports). It is **not deployed** (its `vercel.json`/`package.json` are stale) and should be treated as historical reference only, not a place to add features.
- **`data/`** (repo root) — source-of-truth spreadsheet: **`חכמי_ישראל.xlsx`** (522+ rows, the file a human edits), plus `*.docx` research documents. `nextjs-app/public/data.json` is *generated from* the xlsx, not the other way around. Note there are two similarly-named workbooks: `חכמי_ישראל.xlsx` (underscore) is the master; `חכמי ישראל.xlsx` (space) is an older 405-row subset with 14 empty columns. The `.csv` is a corrupted derivative — see the pipeline section.
- **`supabase/`** (repo root) — SQL migrations for a separate "Personal Area" feature (user profiles, quotas). `migrations/` is applied by the Supabase CLI in filename order; `rollbacks/` and `tests/` are kept out of the migrations directory on purpose so the CLI doesn't auto-run them. As of this writing only Milestone 1 (schema + RLS) exists — no API routes or UI consume it yet.

Everything below refers to `nextjs-app/` unless stated otherwise.

## Commands

Run from `nextjs-app/`:

```bash
npm run dev          # Next.js dev server (localhost:3000)
npm run build         # production build — do this before pushing anything touching data.json,
                      # AppShell.tsx, or the viz components; it catches type errors tsc alone can miss
npm run start         # serve the production build locally (useful for testing Leaflet init and data-load timing)
npm run type-check    # tsc --noEmit
npm test              # tests/*.test.ts via tsx (rag, chat wiring, geo layers, url state, sefaria, wikipedia, youtube, automatic answer, pwa, quiz, kids, share card, read-aloud, today, catalogue links, paper links, tower, en/ru profiles and terms)
```

There is no linter wired up (`eslint: { ignoreDuringBuilds: true }` in `next.config.ts`). There is a small test suite: `npm test` runs the `tsx` scripts in `tests/` (RAG retrieval, chat wiring, geo layers, URL state, the Sefaria/Wikipedia/YouTube side files, the automatic answer, the installable app, the quiz, the kids' journey) with no framework. Treat a clean `npm run type-check`, `npm test` and `npm run build` as the bar for "done."

Deployment is automatic: push to `main` → GitHub Action (`.github/workflows/deploy.yml`) builds `nextjs-app/` and deploys to Vercel. There's no staging branch; `main` is production.

## Architecture

### Data pipeline: XLSX → data.json → app

1. **`data/חכמי_ישראל.xlsx` is the canonical source**, read directly by `rebuild_data_from_csv.py` via openpyxl. The sibling `.csv` is **not** a valid source and is no longer a build input: it was produced by merging this file's rows into a different sheet's column layout, and that merge reassigned ids — of 364 sages present in both, 348 ended up with different ids. Building from it silently attached the wrong research documents to ~91% of sage pages.

   Each row has a `מזהה` (id) column — **this id is the stable identity key across the entire system**: it's reused verbatim as the sage's `id` in `data.json`, the filename for research docs (`public/research/<id>.json`), the key in `data-patch.json`, and the key in `data/sage-id-aliases-*.json`. Never renumber an existing id — that breaks all four at once, silently, with no build error. When you must reconcile two datasets, **join on name, not on id**: names are stable across id spaces, ids are exactly what drifts. The same id can appear on multiple rows (one person can have several "episode" rows); dedupe by name, not by id, when rebuilding.
2. **`public/data.json`** (`{ nodes: Sage[], links: Connection[] }`) is the canonical dataset consumed by the app. Raw node fields (`era`, `era_key`, `era_label`, `central_idea`, `chapter_type`, comma-string `tags`) get remapped to the `Sage` type by `lib/dataFoundation.ts::normalizeSage`, shared by `lib/serverData.ts` (server) and `lib/appShellDataLoader.ts` (client). Both then copy the result into `Sage` objects through an explicit field list — those two lists must stay in sync if you add a field, or the field is dropped silently on one side.
3. **`era_key`** must be one of the 11 `Period` values in `lib/types.ts` (`patriarchs…modern`). All 11 are now populated. `rebuild_data_from_csv.py` checks `BIBLICAL_RULES` *before* the general `RULES`, against the era label and the years column joined, because the spreadsheet often puts the generic label in `תקופה` ("תנ״ך") and the actual sub-period in `שנים/תקופה` ("תקופת השופטים"). Those rules key on **period phrases only, never bare personal names** — a bare name misfiles later rabbis, since רבי דוד קמחי is not King David and רבי ישעיה די טראני is not the prophet. Keep that constraint if you extend them. When mapping a new free-text era label, check `data.json` for an existing `era_label → era_key` precedent before guessing.
4. **`data-patch.json`** applies small per-id field overrides. It is applied on **both** paths — client-side in `AppShell.tsx` and server-side in `lib/serverData.ts` (which imports it and calls `applyPatches`). An earlier version of this file claimed the patch was client-only; that was wrong, and the error hid a real corruption for months: the patch held `period`/`birth_year` overrides keyed to a dead id space, forcing the Kaliver Rebbe (1923–2019) into `judges` with `birth_year: -1110` on every surface. Because ids are the join key, **any per-id side file becomes actively harmful the moment the id space shifts.** Audit this file whenever ids move.
5. `data-supplement.json`, `data-supplement-2.json`, and `data-ancient.json` **do exist** and are merged over `data.json` at load time (~21 extra sages, so the app shows more than `data.json` alone contains). A previous version of this file declared them deleted; they were not. They are the reason the live sage count exceeds the master count. New sages should still go in the master spreadsheet rather than here.
6. Research documents: `public/research/<id>.json` (Hebrew, canonical) plus optional `<id>.en.json` / `<id>.ru.json` translations, each an array of `{ title, source_file, word_count, content }`. Served two ways: `ResearchSection.tsx` fetches `/research/<id>.<locale>.json` directly (static file, falls back to Hebrew on 404), and `app/api/research/[id]/route.ts` exists as an alternate lazy-loading path with a 1-day cache header. Translations are produced by an offline script against the Claude API (see the `nextjs-app/public/research/` directory) — never invent a translation by hand-editing content, and never delete/gitignore a translation file without explicit approval, since the two locale files are the deliverable of a paid batch job. **Two sources of translations**: the API script (`scripts/character-factory/translate_research.py`) and, since 2026-10-13, the no-API line-aligned workflow in `scripts/translate_lines/` (README there): with no key, the assistant and sub-agents translated the Hebrew papers themselves, a numbered unit per unique Hebrew line, validated and assembled by `tx_build.py` so the line structure `lib/researchParse.ts` relies on is kept exactly (`tx_status.py` prints coverage, `tx_verify.py` re-checks). The English and Russian files that existed before that work are older and have another line layout. Rules that held: translate what the Hebrew says, slips and all (several papers, e.g. 39, 47, 288, 294, 344, carry typos or OCR damage in the Hebrew: fix the Hebrew paper first, then re-translate); names follow `scripts/translate_lines/glossary.md` and the site's overlay (`public/i18n/sages.<locale>.json`); existing translation files are immutable. Coverage: since 2026-10-13 every one of the 445 papers has an English and a Russian file. Six older files that covered only part of their paper (English 99, 167, 312, 403, 608; Russian 484) were replaced with full translations on the owner's say-so; the remaining older files (English 68, 141, 151, 161, 277, 481, 483) are complete but use another line layout, so `tx_verify.py` reports a line-count difference for them. A paper can hold a Russian summary paragraph (about 16 do): `tx_prepare.py` marks it `(en only)`, English translates it, Russian keeps it. Source problems found while translating, to fix in the Hebrew paper and then re-translate: 431's second document is the Rashbatz paper (the same text as 434); 61 (R. Yisrael Alnakawa) carries 58's paper about his son; the second half of 138 (Rav Uziel) is about R. Elazar Azikri; 426 and 430 contain text-generator leftovers ("Starting Video Overview generation."); 564's title is cut off ("nathan Sacks"). The work files live outside the repo (`$TX_WORK`).
7. **Links to a sage's writings elsewhere** (two generated, per-id side files, like `data-patch.json`: never hand-edit them, regenerate). Both match the roster to the outside catalogue by *name* and accept a match only when birth/death years agree (or, for people with no years, when the name is exactly his and unique), so a homonym is not linked; the matching helpers shared by both scripts live in `scripts/sage_names.py`. Each entry stores the roster label it was matched on, and the tests (`tests/sefaria.test.ts`, `tests/wikipedia.test.ts`) fail when an id now belongs to a different sage or two sages share a page.
   - `public/data-sefaria.json` ← `python3 scripts/build_sefaria_links.py [--report]`: the sage's author (or person) page on sefaria.org, the works Sefaria lists under it, and the Wikipedia titles Sefaria links for him. Uses Sefaria's topic list, then its name search.
   - `public/data-wikipedia.json` ← `python3 scripts/build_wikidata_links.py [--report]`: his Hebrew and English Wikipedia articles and his Hebrew Wikisource author page (`מחבר:…` only), via Hebrew Wikipedia and Wikidata. **Wikimedia rate-limits shared addresses hard** (a request a second gets 429 and a 20 s wait), so the script batches (50 titles / 20 items per request), paces itself at 3 s, honours Retry-After and caches under `--cache`; a full run takes about 45 minutes from the cloud environment, a cached re-run takes seconds.
   - `lib/sefaria.ts`, `lib/wikipedia.ts` read them (bundled at build time; `wikiLinks()` prefers Wikidata's match and falls back to the Wikipedia titles Sefaria holds). `components/sages/WritingsSection.tsx` renders the "כתבים בספריא" / "כתבים בוויקיטקסט" section on the sage page, and the page footer links the exact Wikipedia articles. A sage with no match keeps the generic search links.
8. **YouTube videos of the sages** (`public/data-youtube.json`, another generated per-id side file). The site owner keeps a YouTube playlist of sage videos (724 uploads: one Russian and one English video per sage, plus a few Hebrew). Which video belongs to which sage is a **hand-checked map**, not a script's guess: the titles are English/Russian/Hebrew renderings of a name and the roster's labels are Hebrew. `data/youtube-playlist.tsv` is a snapshot of the playlist, `data/youtube-sage-map.json` maps sage ids to its rows and lists in `_left_out` what was deliberately not matched. `python3 scripts/build_youtube_links.py [--check]` writes the data file; `--check` asks `youtube.com/oembed` whether each video can be embedded. Every row that names a roster sage is kept (a sage can have several videos in a language, as the Ramban has three in each: the page shows the first two and tucks the rest under "more videos"); a title can name the sage by a formal name the roster does not use (the Vilna Gaon is `רבי אליהו בן שלמה זלמן`), so check the sage's research document (`public/research/<id>.json`) before leaving a row out. Six playlist sages the roster lacked (Bokrat 627, Miriam 629, Abbahu 623, Imma Shalom 624, Berdugo 625, Nathan Shapira 626) were added from the owner's Drive papers and Spotify episodes and their rows attached; rows 451-452 ("Religious Authority … in Ancient Rome") are Theodos of Rome (485), as the owner confirmed. Two lessons on the weekly portion Ekev (rows 79-80) stay out on the owner's instruction, and Shabtai Ben-Dov (670-672) and Yehuda Gurland (682) are not in the roster and have no paper. **A video's language is its own `defaultLanguage`, read through the YouTube Data API.** The playlist view translates titles to the viewer's language (yt-dlp, a browser and the oEmbed endpoint all show the English title of a Russian video), so two videos of a sage both look English there; the API's `snippet.title` and `snippet.defaultLanguage` are the original (`ru`, `en`, `iw` = Hebrew, which is how 356 / 349 / 19 of the 724 split). The owner listened to five pairs (Rashi, R. Jacob Landau, the Shach: Russian first; Rabbeinu Perachiah and the Meshech Chochmah: English first) and the field matched all five, and the order flips from pair to pair, so never infer a language from position, duration or title style (an earlier guess by position was wrong for 27 of 82 rows). `data/youtube-playlist.tsv` therefore holds the original title and language; refresh it with `python3 scripts/snapshot_youtube.py [--write]`, which needs the API key (the cloud environment's network secret adds it as `X-Goog-Api-Key` for `youtube.googleapis.com`; elsewhere set `$YOUTUBE_API_KEY`) and refuses to write when the rows moved, because `data/youtube-sage-map.json` is keyed by row. `defaultAudioLanguage` is `ru` on every upload (the channel's default), so it says nothing. The video pages and `www.youtube.com` itself still refuse the cloud sandbox (Google's "sorry" page). A video is only ever shown on the page of its own language (`lib/youtube.ts::sageVideos`). `components/sages/YoutubeWatch.tsx` is a click-to-load facade (nothing is requested from YouTube until the visitor presses play; the player is `youtube-nocookie.com`), used on the sage page (`#video`) and, for the site's introduction video (`INTRO_VIDEO` in `lib/youtube.ts`, empty until uploaded), on the About page. `tests/youtube.test.ts` fails when an id now belongs to another sage.

9. **Teacher, student and family links from Sefaria and Wikidata** (`public/data-catalog-links.json`, a generated supplement file merged over `data.json` on both paths, like `data-research-links.json`; never hand-edit it). `python3 scripts/build_catalog_links.py [--report]` reads Sefaria's topic links (taught / learned-from, parent / child / grandparent / ancestor / sibling / spouse / cousin / in-law, opposed, corresponded-with) and Wikidata's claims (student of P1066, student P802, father, mother, child, sibling, spouse, relative, influenced by) **between sages already on the roster**. Which Sefaria topic and Wikidata item is which sage is not decided there: it takes them from `data-sefaria.json` and `data-wikipedia.json`, and refuses to run when either has drifted from the roster labels. Direction follows the site's convention (`teacher` source = the teacher, `family` source = the elder relative). Checked like the spreadsheet's links but never flipped, and only on exact dates, since a century-precision sage's `birth_year` is the start of a window (the Rosh is 1200–1400): teacher younger than student dropped, lifetimes that never overlap or births over 90 years apart kept as influence, the catalogues or the site disagreeing on who taught whom dropped, a link the site already states not repeated, two book entries (`מחזור ויטרי`, `מדרש רבה`) never an end. Every decision is in `data/catalog_links_report.txt`. First run (2026-10-13): 128 links (95 teacher, 29 family, 2 influence, 2 colleague); teacher/student links on the site went from 31 to 126, family from 18 to 47, sages with no link at all from 110 to 98. Each entry stores both roster labels, and `tests/catalogLinks.test.ts` fails when an id now belongs to someone else. **`mergeDatasets` keeps one edge per relation**: a pair with a teacher, student or family link drops its influence link, and teacher X→Y with student Y→X is kept once, so the network graph does not draw two edges (or count a sage twice) for one relation; the sage page and the lineage tree already chose the strongest link per pair.

10. **Teacher and family links the research papers state** (`public/data-paper-links.json`, another generated supplement merged on both paths; never hand-edit it). Built by `python3 scripts/build_paper_links.py [--report] [--check]` from `data/links-from-research.json`, a reviewed list `{paper, a, b, a_label, b_label, type: teacher|family, relation, quote}`: on 2026-10-13 sub-agents read, in each paper, the sentences with a relation word (רבו, תלמידו, אביו, חתנו …) that name another roster sage, and recorded only what the paper states **for its own sage**: personal teaching (not learning from his books, not ordination, not "his school"), and family with `relation` naming a's role towards b, the elder first (father, grandfather, father-in-law, uncle, ancestor; brother, husband, cousin, brother-in-law, relative). Left out: what the paper doubts or calls a tradition it does not accept, namesakes (Aboab I is not Beirav's teacher), co-parents-in-law (מחותנים), relations inferred rather than stated, a book title in the sources list. Papers known to be about someone else (61, 81, 138, 192, 431) were not read. The build keeps an entry only while its quote is in the paper and both ids carry the labels they were read under, applies the same exact-date checks as the catalogue links (a teacher younger than his student is dropped, not flipped), and drops a relation another file states the other way round; a relation already on the site is not repeated. Every decision is in `data/paper_links_report.txt`. First run: 449 relations read, 211 links (128 teacher, 83 family). With the catalogue links: links 492 → 682, teacher/student 31 → 254, family 18 → 130, sages with no link 110 → 82. **Fixed on the way:** `data.json` had R. Yaakov Margolis of Nuremberg (453) as the student of R. Yaakov Polak (457), an edge the rebuild recovers from `data.json.backup_v4`; both papers say the reverse (457: "רבו מובהק של פולק, רבי יעקב מרגליות מנירנברג"). The right link is now a curated one in `data-research-links.json`, so the rebuild drops the wrong edge (rule 4 above `TS = ...`) and its CSV influence twin, and both were taken out of the two copies of `data.json` to match what a rebuild writes.

### The assistant (chat)

`POST /api/chat` answers with the language model (needs `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY` and the quota tables and RPCs in Supabase). The owner's plan: the model is switched on only when there is demand, funded by users (a symbolic payment towards the API, on top of the per-user quotas); until then the site answers automatically. **With no `ANTHROPIC_API_KEY` the route skips the auth and quota stores and answers automatically at once; and whenever the model path fails with a 5xx** (no key, no quota store, provider down or slow), the route answers anyway with the *automatic answer*: `lib/rag/referralAnswer.ts` is a **referral, not an answer, and not an apology**: it names the sage the question is about, says who he is in one sentence (the dataset's own summary in the question's language, never a quote of the research), cites the one research passage closest to the question (a handle the widget numbers and links to its heading), and returns `links` (his page, the research, the episode, the video of that language, the writings, up to three relatives) that `ChatWidget` shows as "go further" chips; only sections the page really has get a chip. It never says the assistant is unavailable (the owner asked for that). The response carries `mode: 'referral'`, costs nothing and is not counted against the quota. A name that fits several sages gets a chip for each page; a question naming nobody says so. 4xx (a spent quota, an invalid session) are not turned into answers. Don't turn a model failure back into a bare 500: on 2026-10-11 production returned `500 internal_error` for every question (the quota-check `GET` still answered 200, so the widget looked healthy) and the cause was only visible in the Vercel runtime logs. The search box offers the assistant as its own row (`SearchBar` → `askQuestion()` in `components/chat/askAbout.ts` → `ChatWidget` opens unscoped and sends it); a text that reads as a question (`looksLikeQuestion`) puts that row first. Sages are matched in the question by their Hebrew name and, through `lib/rag/buildContext.ts::localNamesFor`, by the English/Russian overlay label (a Russian name also with a case ending). A name inside a longer name the question holds is not a mention of its own ("Shmuel HaNagid" is not also Shmuel the Amora), epithets ("King", "prophetess", "царь") are not names, and among the sages found by a single word, the one more of whose name the question holds comes first (the first sage is the one the answer leads with). `tests/automaticAnswer.test.ts` covers all of it.

### Demand analytics and the installable app (PWA)

Added on 2026-10-12 to answer one question before anyone builds a store app or switches the paid assistant on: **do people use the site, on phones, and do they come back?** Nothing here shows anything to a visitor except the install button.

- **Analytics** is Vercel Web Analytics, cookie-free (no banner). `components/layout/SiteTelemetry.tsx`, rendered once by `app/[locale]/layout.tsx`, mounts `<Analytics />`. It gives page views, devices, countries, referrers and UTM tags without further code. **It records nothing until Web Analytics is switched on for the project in the Vercel dashboard** (project `ozar-chachamim-app` → Analytics → Enable); it needs no key. The old `lib/analytics.ts` (a `dataLayer` writer nobody imported) is gone.
- **Custom events** go through `lib/analytics.ts::track(name, props)`: `video_play`, `listen_load` (the YouTube / Spotify facades were pressed), `quiz_start`, `quiz_complete`, `kids_station_done`, `chat_open`, `chat_question` (`{locale, mode: model|referral}`), `tab_view` (`{tab}`, from `setActiveTab`), `research_listen` (`{locale, lang}`: the read-aloud player started), `today_share` (`{locale, method}`), `tower_share` (`{locale, method: share|copy}`), `return_visit` (`{visits: '2'..'10+'}`: a localStorage counter of distinct visit days, no identifier, because "returning visitors" is not a native Vercel metric), `pwa_prompt_available`, `pwa_install_click`, `pwa_install_choice`, `pwa_installed`, `pwa_open`. `AnalyticsEvent` is the closed list: add a name there first. **An event never carries a question, a sage name or an id**, only a name and coarse properties. `track()` does nothing outside production and never throws. Vercel records custom events only on plans that support them (Pro); on a plan that doesn't, `track()` is harmless and records nothing, and page views, device split and the `utm_source=pwa` split still work.
- **Reading demand**: mobile share (Devices), languages (Pages: `/he` `/en` `/ru`), countries, referrers, and with custom events `return_visit` / unique visitors, `video_play` and `listen_load` per visitor, `chat_open`, installs. The thresholds the owner and I settled on before building a store app: at least ~60% of visits on mobile, ~25% of visitors returning within a month, and a visible number of installs; below that, a store app is a cost without a reader. Those numbers are judgement, not market fact: revisit them with the data.
- **Installable app**: `app/manifest.ts` (served at `/manifest.webmanifest`; the only Hebrew-only string set: a manifest has one name; `start_url` carries `utm_source=pwa` so installed visits show apart), `public/icons/icon-192.png`, `icon-512.png`, `maskable-512.png` and `app/apple-icon.png` (all cut from `public/images/temple-medallion.png` with Pillow; maskable keeps the medallion inside the 62% safe zone), `public/sw.js`, `public/offline.html` (static, he/en/ru by the browser's language). `next.config.ts` serves `/sw.js` with `Cache-Control: max-age=0, must-revalidate` and `Service-Worker-Allowed: /`: without that a fix to the worker would not reach visitors for a day.
- **Install button** (`components/ui/InstallApp.tsx`, state in `lib/pwaInstall.ts`): shown only when it can do something. Chrome, Edge and Samsung Internet fire `beforeinstallprompt` once and early, so `lib/pwaInstall.ts` registers its listener when the module loads and keeps the event for any button. Safari on iOS has no prompt: the button (mobile menu, About page) shows the "Share → Add to Home Screen" steps instead, and the desktop header hides it there. Nothing is shown once installed. Where it sits: header (desktop, icon only), the mobile ⋯ menu, the About page.
- **Service worker rules** (`public/sw.js`, covered by `tests/pwa.test.ts`, which runs the real file in a sandbox): `/api/*` and `/auth/*` and other origins are **never** touched (chat answers, quota and sign-in must not be cached; YouTube/Spotify/Leaflet tiles are not ours); `/_next/static/*` cache-first (hashed names); `data*.json` and `i18n/*` network-first (an edited dataset must show at once, not one visit late) with the saved copy when offline or when the network takes over 4 s; `research/*.json` and `quiz/*.json` the same but in their own cache capped at 80 files (15 MB in total); icons, images and the kids' illustrations stale-while-revalidate; navigations network-first, the last good 200 (never a redirect) kept per URL, `/offline.html` when there is neither. It registers in production only (in development it would serve stale files). To drop everything every visitor holds, bump `VERSION` in `sw.js`. A change to what the worker caches needs a test: a worker that caches the wrong thing breaks the live site quietly, and only for returning visitors.
- **Not done on purpose**: no push notifications (iOS needs a Home Screen install first, and nothing here has a reason to notify yet), no Capacitor/store wrapper (decide from the numbers above; Apple's guideline 4.2 rejects a thin web wrapper, so a store app would need native value: sage of the day, offline reading, sharing).

### Share card and read-aloud (added 2026-10-13)

- **Share card**: `app/[locale]/sage/[id]/opengraph-image.tsx` draws the 1200×630 image WhatsApp, Telegram, Facebook and X show for a sage's page, in the page's language (name, subtitle, era, years, what the page holds: research, video, episode, quiz, and the medallion), on request, cached by the CDN; the page sets `twitter: summary_large_image`. Satori (next/og) has **no right-to-left layout**: Hebrew is drawn as one box per word in a `row-reverse` wrapping row, each word already in visual order (`lib/ogText.ts`: letters reversed, brackets mirrored, digit/Latin runs left as they are; an en dash between years reverses them as a browser does). Fonts and the medallion are in `nextjs-app/assets/og/` (OFL; traced in `next.config.ts`); keep the PNG under ~300 KB (WhatsApp drops larger previews), which is why the background is flat. `tests/share.test.ts`.
- **Listen to the research**: `components/sages/ListenResearch.tsx` in the reader's header reads the papers aloud with the browser's own voice (Web Speech API: free, nothing sent anywhere), starting where the reader is, lighting up (`.speaking`) and following the piece it reads; pause, speed (kept in localStorage `ozar-listen-rate`), stop. What is read and in what pieces is `lib/speech.ts` (title, headings, paragraphs, quotes, list items; no citation markers, URLs, tables or sources; sentences of at most ~240 characters, since some browsers cut a long utterance). The blocks carry `data-speak` (`ResearchBlocks.tsx`) for it to find them. The button shows only when the device has a voice for the paper's language (Hebrew: most phones; desktop Chrome on Linux has none). The first utterance is spoken inside the click (iOS speaks only in a user gesture). Event `research_listen` `{locale, lang}`. `tests/listen.test.ts`.

### Today page: hillula and sage of the day (added 2026-10-13)

- **`/[locale]/today`** (`app/[locale]/today/page.tsx`, rebuilt every 30 minutes): today's Hebrew date (Intl's Hebrew calendar, Israel time; the day turns at midnight, not nightfall), the sages whose **hillula** (yahrzeit) is today, else a **sage of the day**, the hillulot of the coming 30 days, and sharing: an image for a WhatsApp status or story (`app/[locale]/today/story/route.tsx`, 1080×1920, shared through the phone's share sheet with the file, or saved) and a WhatsApp message whose link preview is the sage's share card. Entry points: 📅 in the desktop header and an item in the mobile ⋯ menu; in the sitemap in all three languages. Event `today_share` `{locale, method: image|download|whatsapp|video|video_download}`.

### Tower of Generations (`/[locale]/tower`, added 2026-10-14)

The whole corpus in 3D: **height is time** (piecewise, so the full centuries get the height: `lib/tower.ts::heightOf`), **direction is region** (ten sectors around the axis, map neighbours next to each other: Eretz Israel, Middle East, North Africa, Sepharad, Provence, France, Italy, Ashkenaz, Eastern Europe, other), and a cone that widens with time. ### The sage quiz

A "get to know the sage" quiz on the sage page (`components/sages/SageQuiz.tsx`, section `#quiz` after the research, plus a "חידון" chip in the page header). The game itself is `components/quiz/QuizPlayer.tsx`, shared with the kids' station quizzes (below): length, progress store, wording and the `kind` (`sage` | `kids`) carried on the events are its props. Twenty questions drawn from the sage's research paper, one at a time, each answered with a short explanation; 100 points in all; 0–3 stars at 50 / 75 / 90 (`lib/quiz.ts::STAR_THRESHOLDS`). The owner asked for the schema of a school quiz importer, kept exactly: each question is `{ question, options, correctIndex, explanation, points }`, and two options make a true/false question (kept in order, "true" first; multiple-choice options are reshuffled every game by `shuffleForPlay`). Nothing is fetched until the visitor starts. The best result per sage stays in the browser only (`lib/quizProgress.ts`, localStorage `ozar-quiz-progress`): that is the "journey passport", counted on the result screen. Events `quiz_start` and `quiz_complete` (`{locale, kind, score, stars}`).

- **Files**: `public/quiz/<id>.json` (Hebrew), `<id>.en.json`, `<id>.ru.json`, each `{ label, questions }`. `public/data-quiz.json` is the index the server bundles to decide whether a page has a quiz in its language (a quiz is never shown in another language). Another per-id side file: the label guards against ids drifting, and `tests/quiz.test.ts` fails when an id now belongs to another sage, when a file breaks a rule, or when the index and the files disagree. Never hand-edit a quiz's id or label; regenerate. The English and Russian quizzes of the 22 sages that have a Hebrew quiz are translations of the Hebrew quiz (`scripts/translate_lines/tx_quiz.py`): same questions, `correctIndex`, `points` and label (the Hebrew roster label in every language), names as in that sage's research translation; a sage without a Hebrew quiz has none in en/ru either.
- **Rules** (`lib/quiz.ts::validateQuiz`, mirrored in `scripts/build_quiz.py::validate`): exactly 20 questions (10 for a kids' station quiz: `validateQuiz(quiz, KIDS_QUIZ_LENGTH)`), 2 to 4 distinct options, a `correctIndex` that is an option, an explanation, positive whole points adding up to exactly 100.
- **Generation**: `scripts/build_quiz.py` sends the research paper (citation markers and the closing source list stripped; a dash line is often only a section break, so only a final section of links is cut, and a document stored twice is sent once) to the Claude API as a Message Batch, with the prompt in `scripts/quiz_prompt.md` (adapted from the owner's school prompt: 6 true/false, 10 medium and 4 hard multiple-choice, answerable from the paper alone, doubtful claims left out, explanations in the paper's terms, Hebrew with proper gershayim). The model marks each question easy/medium/hard; the script assigns 3/5/8 points scaled to exactly 100, so the model never does the arithmetic. `--submit` (records the batch in `data/quiz-batches.json`), `--collect <batch>` (writes, validates, reports the failures to resubmit), `--index` (no API: validates every file and rebuilds the index), `--dry-run`. `--lang en|ru` writes the quiz in that language from the Hebrew paper. It needs an API key, which the cloud environment does not have; a full Hebrew run is ~445 papers.
- **Written in session so far (22)**: the pilot, the Rambam (41), Rashi (594) and Dunash ben Labrat (198), to settle the format before a full run; then every other sage a kids' station links to (592, 507, 346, 437, 573, 585, 72, 428, 130, 143, 156, 629, 389, 282, 556, 534, 524, 510, 496), so a child who follows a station's link finds a quiz there. All were written from the paper as `research_text()` sends it, under the same prompt (the 6/10/4 mix, about three true and three false, the right answer's position spread over the four options, claims the paper itself hedges or that look doubtful left out) and through the same `to_quiz` path. Their style is what the batch will reproduce: review them before generating the rest.
- The service worker keeps quizzes in the research cache, so a quiz once played can be played again offline.

### Client data loading: static pipeline only

`AppShell.tsx`'s bootstrap calls `loadAppShellData()`, which fetches `data.json`, the supplements and `data-patch.json` in parallel and merges them with the same `mergeDatasets`/`applyPatches` the server uses, so the home page and the sage pages always show the same corpus. It does **not** read Supabase. It used to fetch Supabase first (`sages_with_stats` / `connections_with_names`) and prefer it whenever it held ≥300 sages and ≥100 links. That made every visitor wait on Supabase, with no timeout, before anything rendered. And because production Supabase holds an old snapshot (missing ~100 current sages such as Rashi, and carrying links deleted since), that stale data won. Don't reintroduce a Supabase read for the public graph. Supabase is a separate, independently populated store, used for auth, chat and the personal area. Search doesn't touch it either: `SearchBar` ranks the loaded sages with `lib/search.ts::searchSagesRanked` and, in the moment before the static data arrives, shows a loading state (the old Supabase `searchSages` fallback is gone). The individual sage page (`app/[locale]/sage/[id]/page.tsx`) is server-rendered and reads **only** `data.json` via `lib/serverData.ts` (bundled at build time, not fetched over HTTP — `public/` isn't readable via `fs` in Vercel's serverless functions). It never touches Supabase.

### Visualization tabs

`AppShell.tsx` orchestrates seven tabs (`Tab` type in `lib/types.ts`): network graph, geography map, traditions, table, timeline, genealogy tree, about. Two different mounting strategies are in play — worth knowing before debugging a "tab shows nothing" report:
- **Graph and map tabs stay mounted permanently**, just toggled via a `hidden`/`block` CSS class, so their data-loading `useEffect`s fire once on initial app load regardless of which tab is active.
- **Traditions, timeline, table, genealogy, about are conditionally rendered** (`{activeTab === 'x' && <Component/>}`) — they mount fresh each time the user switches to them.

`GeoMap.tsx` (Leaflet) depends on its container having non-zero size at init; because it's always-mounted it can initialize while `display:none`, so it explicitly calls `map.invalidateSize()` on an `activeTab`-change effect to recover. `NetworkGraph.tsx` runs d3-force on its own internal timer and renders from `sim.on('tick', …)`. If you ever switch it to manual stepping, remember that d3-force only dispatches `'tick'` when its own timer runs, **not** on manual `.tick()` calls, so the per-tick DOM update must then be called directly. `GenealogyTree.tsx` runs no simulation (it used to: a force layout of every sage in era bands). It is a lineage explorer centred on one focus sage: the pure module `components/viz/lineage.ts` orients the lineage links (teacher/student, influence, predecessor, family) upper → lower, draws a link stored against the chronology in date order, builds the tree a generation at a time up and down (a sage reached twice is drawn once and then as a repeat reference, so cycles end), and lays it out as a tidy top-down tree or, below 700px, an indented outline. The component only joins, transitions and zooms with d3.

### State

Single Zustand store (`store/useAppStore.ts`): sages/connections/sageMap, selection, active tab, theme (persisted to `localStorage`), and filter state (period/region/field/free-text search via `lib/search.ts`'s Hebrew-aware fuzzy matcher — nikud/gershayim/final-letter insensitive). ### Content conventions (data, not code, but frequently touched together)

- **Period keys**: `patriarchs, exodus, judges, kings, second-temple, tannaim, amoraim, geonim, rishonim, acharonim, modern` (`lib/types.ts::ALL_PERIODS`, chronological order — this order drives the timeline band layout, and orients lineage links between undated sages in the genealogy tree).
- **Connection types**: `student, teacher, colleague, influence, oppose, predecessor, contemporary, family`.
  Direction matters for the two lineage types: `teacher` means **source is the teacher of target**, `student` means **source is the student of target**. Any UI that labels a related sage ("רבו" / "תלמידו") must look at which end of the link the current sage is on. `rebuild_data_from_csv.py` validates teacher/student links on every build: it flips a teacher born after the student, downgrades pairs whose lifetimes can't overlap to `influence`, and drops non-person ends and contradictory pairs. The rules are in the comment block above `TS = ('teacher', 'student')`. Every change goes to `data/link_validation_report.txt` for human review; don't edit that report by hand. `influence` means **source influenced target**. Most influence links come from the spreadsheet's "דמויות/השפעות קשורות" column, which lists predecessors and successors alike, so the rebuild orients each one earlier → later, and resolves its names with `find_related`: whole-word matching, no bare given names inside longer phrases ("ספר שמואל" is not שמואל האמורא), and era-checked disambiguation. `find_node`'s looser matching is kept for the curated-link recovery, which was calibrated against it.
- **Region keys**: `ashkenaz, east-europe, tsarfat, provence, sefarad, italy, north-africa, mizrach, eretz-israel, other` — derived from free-text `location` via `lib/regions.ts::regionsOf` (keyword matching), not stored directly on most sages.
- **Map coordinates** come from one resolver, `lib/locationCoords.ts` (`resolveCoords` / `primaryPlaceOf`), shared by the map markers and the place cohorts. It uses whole-word matching and prefers city over region over country; when a sage has several places at the same level, it takes the one mentioned first. Explicit `lat`/`lng` on a sage wins. Don't add a second place lookup; extend the gazetteer in that file instead.
- Hebrew is written with proper גרשיים (e.g. `רמב״ם`, not `רמבם`), and RTL is the default direction; English/Russian content is LTR overlay only.

When adding research documents from Google Drive to existing sages:

### Setup
1. **Manifest file**: Create or update a JSON manifest at `/tmp/claude-0/-home-user/4ee6b46b-17bb-58f3-a062-e7061ae6d87c/scratchpad/approved_46_minus_7.json` with an array of objects:
   ```json
   [
     {
       "title": "Research title",
       "sage_id": "123",
       "sage_label": "Hebrew sage name",
       "spotify": "https://open.spotify.com/episode/...",
       "drive_id": "Google Drive document ID"
     }
   ]
   ```

2. **Output format**: Each research document is written to `nextjs-app/public/research/<sage_id>.json` as:
   ```json
   [
     {
       "title": "Document title",
       "source_file": "Google Docs: [original title]",
       "word_count": 12345,
       "content": "Full text content of the document..."
     }
   ]
   ```
   If multiple documents exist for the same sage_id, they are appended to the array.

### Process
1. **Triage**: Categorize documents from Google Drive folder into matching sages vs. new candidates
2. **Filter**: Remove sages that don't exist in the data.json (validate FK constraints)
3. **Ingest**: For each approved document:
   - Download Google Doc via Drive API (requires authentication)
   - Extract text content
   - Count words
   - Write JSON file to output directory
   - Append to existing files if sage already has research
4. **Validate**: Verify all JSON files are valid and properly formatted

### Google Drive API Authentication
- Requires Google Drive connector enabled in Claude Code session
- Uses service account or OAuth credentials
- Downloads via `google.drive.files.export` (converts Google Docs to plain text)

### Common Issues
- **API Timeout**: If processing many documents, batch in groups of 10-15 to avoid timeouts
- **Missing Sage**: Validate sage_id exists in `nextjs-app/public/data.json` before ingestion
- **Duplicate Entries**: Check if research already exists for a sage_id; append rather than replace
- **Word Count**: Use simple split on whitespace; emoji/special chars may inflate count slightly

### Environment Variables (`.claude/settings.json`)
- `RESEARCH_MANIFEST_PATH`: Path to approved documents manifest
- `RESEARCH_OUTPUT_DIR`: Target directory for research JSON files (relative to repo root)
