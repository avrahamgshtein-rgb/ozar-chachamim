# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout — read this first

This repo contains **two generations of the same project**. Only one is live:

- **`nextjs-app/`** — the active, deployed app (Next.js 15 + React 19). `.github/workflows/deploy.yml` builds and deploys *this* directory to Vercel on every push to `main`. All feature work happens here.
- **Repo root** (everything outside `nextjs-app/`) — a legacy vanilla-JS/Supabase prototype (`index.html`, `graph.js`, `styles-graph.css`, dozens of one-off `*.md` status reports, migration scripts, scratch JSON exports). It is **not deployed** (its `vercel.json`/`package.json` are stale) and should be treated as historical reference only, not a place to add features.
- **`data/`** (repo root) — source-of-truth spreadsheet: **`חכמי_ישראל.xlsx`** (679 sages, one row each, the file a human edits), plus `*.docx` research documents. `nextjs-app/public/data.json` is *generated from* the xlsx, not the other way around. Note there are two similarly-named workbooks: `חכמי_ישראל.xlsx` (underscore) is the master; `חכמי ישראל.xlsx` (space) is an older 405-row subset with 14 empty columns. The `.csv` is a corrupted derivative — see the pipeline section.
- **`supabase/`** (repo root) — SQL migrations for a separate "Personal Area" feature (user profiles, quotas). `migrations/` is applied by the Supabase CLI in filename order; `rollbacks/` and `tests/` are kept out of the migrations directory on purpose so the CLI doesn't auto-run them. As of this writing only Milestone 1 (schema + RLS) exists — no API routes or UI consume it yet.

Everything below refers to `nextjs-app/` unless stated otherwise.

## Working method: plan, delegate, review, grade (the owner's instruction, 2026-10-14)

The owner asked for every writing and development task to run this way from now on. This is standing permission to use sub-agents for them; other work (answering a question, a small lookup) does not need it.

1. **Plan (main agent).** Write a detailed plan:
   - the goal in the owner's words;
   - the files to touch and the approach;
   - the rules from this file that apply;
   - numbered **acceptance criteria**, each one checkable (a test, a command, a screenshot);
   - what is out of scope.
2. **Delegate.** Execution is Sonnet's, in two agent definitions under `.claude/agents/` (if a name is not listed as an agent type because the session started before the file existed, use the general-purpose agent with `model: sonnet` and paste that file's instructions into the prompt):
   - **`lead`** is Sonnet's own lead developer. Hand it the plan; it returns a split into work packages, each owning its files (no two packages touch the same file; shared files such as `package.json`, `CLAUDE.md` and `lib/analytics.ts` stay with the lead), with the interfaces between them agreed up front.
   - **`developer`** workers build the packages **in parallel**: spawn them all in one response, one per package, each with its package and the plan's rules. A sub-agent here has no Agent tool (tested 2026-10-14), so the main agent presses the spawn button for the lead; the lead still owns the split and the integration. Workers run only `type-check` and their own test file, never the full suite, the build or a server, so parallel builds never collide.
   - When the workers report, message the **same** `lead` (SendMessage keeps its context) with their reports: it reads their diffs, wires the pieces together, runs `type-check`, `npm test`, `build` and the browser check, and writes the one consolidated report. A task too small to split goes to the lead alone, or straight to one `developer`.
   - Nobody but the main agent commits or pushes.
3. **Review and grade (main agent).** Do not take the report on trust:
   - read the whole diff;
   - run `npm run type-check`, `npm test` and `npm run build` yourself;
   - check every acceptance criterion;
   - look at visible changes in a browser;
   - re-read the change against this file's rules.
   Give a grade with detailed findings (what is wrong, where, why, what A requires):
   - **A**: every criterion met, all checks green, no findings that matter.
   - **B**: works, but has real gaps (a missing test, an edge case, a rule bent, unclear code).
   - **C**: a criterion unmet or a check failing.
   - **D/F**: wrong or broken.
4. **Iterate.** Send the grade and findings back to the same `lead` (SendMessage, so it keeps its context): it fixes them itself or returns a new split for the workers, then re-runs the checks and reports finding by finding. Review and grade again. Repeat until the work earns an A. If several rounds bring no progress (e.g. after 4), stop and tell the owner what blocks it, rather than looping on.
5. **Finish (main agent).** Commit, push and open the PR as before (one push per feature). Tell the owner the rounds and grades in a line or two.

First run (2026-10-14, the sage riddle, one `developer` before the `lead` existed): round 1 B+ (a pool of obscure sages; a "later era" chip shown for two sages of the same era), round 2 A. Second run (2026-10-14, Six Steps: the `lead` split the plan into four packages, three built in parallel and one after, then integrated): round 1 A.


There is no linter wired up (`eslint: { ignoreDuringBuilds: true }` in `next.config.ts`). There is a small test suite: `npm test` runs the `tsx` scripts in `tests/` (RAG retrieval, chat wiring, geo layers, URL state, the Sefaria/Wikipedia/YouTube side files, the automatic answer, the installable app, the quiz, the kids' journey) with no framework. Treat a clean `npm run type-check`, `npm test` and `npm run build` as the bar for "done."

Deployment is automatic: push to `main` → GitHub Action (`.github/workflows/deploy.yml`) builds `nextjs-app/` and deploys to Vercel. There's no staging branch; `main` is production.

## Architecture

### Data pipeline: XLSX → data.json → app

1. **`data/חכמי_ישראל.xlsx` is the canonical source**, read directly by `rebuild_data_from_csv.py` via openpyxl. The sibling `.csv` is **not** a valid source and is no longer a build input: it was produced by merging this file's rows into a different sheet's column layout, and that merge reassigned ids — of 364 sages present in both, 348 ended up with different ids. Building from it silently attached the wrong research documents to ~91% of sage pages.

   Each row has a `מזהה` (id) column — **this id is the stable identity key across the entire system**: it's reused verbatim as the sage's `id` in `data.json`, the filename for research docs (`public/research/<id>.json`), the key in `data-patch.json`, and the key in `data/sage-id-aliases-*.json`. Never renumber an existing id — that breaks all four at once, silently, with no build error. When you must reconcile two datasets, **join on name, not on id**: names are stable across id spaces, ids are exactly what drifts. The same id can appear on multiple rows (one person can have several "episode" rows); dedupe by name, not by id, when rebuilding.
2. **`public/data.json`** (`{ nodes: Sage[], links: Connection[] }`) is the canonical dataset consumed by the app. Raw node fields (`era`, `era_key`, `era_label`, `central_idea`, `chapter_type`, comma-string `tags`) get remapped to the `Sage` type by `lib/dataFoundation.ts::normalizeSage`, shared by `lib/serverData.ts` (server) and `lib/appShellDataLoader.ts` (client). Both then copy the result into `Sage` objects through an explicit field list — those two lists must stay in sync if you add a field, or the field is dropped silently on one side.
3. **`era_key`** must be one of the 11 `Period` values in `lib/types.ts` (`patriarchs…modern`). All 11 are now populated. `rebuild_data_from_csv.py` checks `BIBLICAL_RULES` *before* the general `RULES`, against the era label and the years column joined, because the spreadsheet often puts the generic label in `תקופה` ("תנ״ך") and the actual sub-period in `שנים/תקופה` ("תקופת השופטים"). Those rules key on **period phrases only, never bare personal names** — a bare name misfiles later rabbis, since רבי דוד קמחי is not King David and רבי ישעיה די טראני is not the prophet. Keep that constraint if you extend them. When mapping a new free-text era label, check `data.json` for an existing `era_label → era_key` precedent before guessing.
4. **`data-patch.json`** applies small per-id field overrides. It is applied on **both** paths — client-side in `AppShell.tsx` and server-side in `lib/serverData.ts` (which imports it and calls `applyPatches`). An earlier version of this file claimed the patch was client-only; that was wrong, and the error hid a real corruption for months: the patch held `period`/`birth_year` overrides keyed to a dead id space, forcing the Kaliver Rebbe (1923–2019) into `judges` with `birth_year: -1110` on every surface. Because ids are the join key, **any per-id side file becomes actively harmful the moment the id space shifts.** Audit this file whenever ids move.
5. `data-supplement.json`, `data-supplement-2.json`, and `data-ancient.json` **do exist** and are merged over `data.json` at load time (~21 extra sages, so the app shows more than `data.json` alone contains). A previous version of this file declared them deleted; they were not. They are the reason the live sage count exceeds the master count. New sages should still go in the master spreadsheet rather than here.
6. Research documents: `public/research/<id>.json` (Hebrew, canonical) plus optional `<id>.en.json` / `<id>.ru.json` translations, each an array of `{ title, source_file, word_count, content }`. Served two ways: `ResearchSection.tsx` fetches `/research/<id>.<locale>.json` directly (static file, falls back to Hebrew on 404), and `app/api/research/[id]/route.ts` exists as an alternate lazy-loading path with a 1-day cache header. Translations are produced by an offline script against the Claude API (see the `nextjs-app/public/research/` directory) — never invent a translation by hand-editing content, and never delete/gitignore a translation file without explicit approval, since the two locale files are the deliverable of a paid batch job. **Two sources of translations**: the API script (`scripts/character-factory/translate_research.py`) and, since 2026-10-13, the no-API line-aligned workflow in `scripts/translate_lines/` (README there): with no key, the assistant and sub-agents translated the Hebrew papers themselves, a numbered unit per unique Hebrew line, validated and assembled by `tx_build.py` so the line structure `lib/researchParse.ts` relies on is kept exactly (`tx_status.py` prints coverage, `tx_verify.py` re-checks). The English and Russian files that existed before that work are older and have another line layout. Rules that held: translate what the Hebrew says, slips and all (several papers, e.g. 39, 47, 288, 294, 344, carry typos or OCR damage in the Hebrew: fix the Hebrew paper first, then re-translate); names follow `scripts/translate_lines/glossary.md` and the site's overlay (`public/i18n/sages.<locale>.json`); existing translation files are immutable. Coverage: since 2026-10-13 every paper has an English and a Russian file (445 papers then; 448 since 2026-10-18, when the owner's papers on 630, 631 and 634 came with their translations). Six older files that covered only part of their paper (English 99, 167, 312, 403, 608; Russian 484) were replaced with full translations on the owner's say-so; the remaining older files (English 68, 141, 151, 161, 277, 481, 483) are complete but use another line layout, so `tx_verify.py` reports a line-count difference for them. A paper can hold a Russian summary paragraph (about 16 do): `tx_prepare.py` marks it `(en only)`, English translates it, Russian keeps it. Source problems found while translating, to fix in the Hebrew paper and then re-translate: 431's second document is the Rashbatz paper (the same text as 434); the second half of 138 (Rav Uziel) is about R. Elazar Azikri; 426 and 430 contain text-generator leftovers ("Starting Video Overview generation."); 564's title is cut off ("nathan Sacks"). **Fixed on 2026-10-18:** 61 (R. Yisrael Alnakawa) carried 58's paper about his son; his Hebrew paper was replaced by the owner's Drive paper on R. Yisrael himself and its English and Russian files were re-translated from it (the one exception to "existing translations are immutable", on the owner's say-so). Slips the translators rendered as written in the papers added that day: 631 unit 7 `ה'של"ל` (5360, after the Ari's death; probably `ה'ש"ל`) and `מהטאטא` (probably `מהחטא`); 630 calls R. The work files live outside the repo (`$TX_WORK`).
7. **Links to a sage's writings elsewhere** (two generated, per-id side files, like `data-patch.json`: never hand-edit them, regenerate). Both match the roster to the outside catalogue by *name* and accept a match only when birth/death years agree (or, for people with no years, when the name is exactly his and unique), so a homonym is not linked; the matching helpers shared by both scripts live in `scripts/sage_names.py`. Each entry stores the roster label it was matched on, and the tests (`tests/sefaria.test.ts`, `tests/wikipedia.test.ts`) fail when an id now belongs to a different sage or two sages share a page.
   - `public/data-sefaria.json` ← `python3 scripts/build_sefaria_links.py [--report]`: the sage's author (or person) page on sefaria.org, the works Sefaria lists under it, and the Wikipedia titles Sefaria links for him. Uses Sefaria's topic list, then its name search.
   - `public/data-wikipedia.json` ← `python3 scripts/build_wikidata_links.py [--report]`: his Hebrew and English Wikipedia articles and his Hebrew Wikisource author page (`מחבר:…` only), via Hebrew Wikipedia and Wikidata. **Wikimedia rate-limits shared addresses hard** (a request a second gets 429 and a 20 s wait), so the script batches (50 titles / 20 items per request), paces itself at 3 s, honours Retry-After and caches under `--cache`; a full run takes about 45 minutes from the cloud environment, a cached re-run takes seconds.
   - `lib/sefaria.ts`, `lib/wikipedia.ts` read them (bundled at build time; `wikiLinks()` prefers Wikidata's match and falls back to the Wikipedia titles Sefaria holds). `components/sages/WritingsSection.tsx` renders the "כתבים בספריא" / "כתבים בוויקיטקסט" section on the sage page, and the page footer links the exact Wikipedia articles. A sage with no match keeps the generic search links.
8. **YouTube videos of the sages** (`public/data-youtube.json`, another generated per-id side file). The site owner keeps a YouTube playlist of sage videos (730 uploads: one Russian and one English video per sage, plus a few Hebrew). Which video belongs to which sage is a **hand-checked map**, not a script's guess: the titles are English/Russian/Hebrew renderings of a name and the roster's labels are Hebrew. `data/youtube-playlist.tsv` is a snapshot of the playlist, `data/youtube-sage-map.json` maps sage ids to its rows and lists in `_left_out` what was deliberately not matched. `python3 scripts/build_youtube_links.py [--check]` writes the data file; `--check` asks `youtube.com/oembed` whether each video can be embedded. Every row that names a roster sage is kept (a sage can have several videos in a language, as the Ramban has three in each: the page shows the first two and tucks the rest under "more videos"); a title can name the sage by a formal name the roster does not use (the Vilna Gaon is `רבי אליהו בן שלמה זלמן`), so check the sage's research document (`public/research/<id>.json`) before leaving a row out. Six playlist sages the roster lacked (Bokrat 627, Miriam 629, Abbahu 623, Imma Shalom 624, Berdugo 625, Nathan Shapira 626) were added from the owner's Drive papers and Spotify episodes and their rows attached; rows 457-458 ("Religious Authority … in Ancient Rome") are Theodos of Rome (485), as the owner confirmed. Two lessons on the weekly portion Ekev (rows 85-86) stay out on the owner's instruction, and Shabtai Ben-Dov (676-678) and Yehuda Gurland (688) are not in the roster and have no paper. **Six uploads of 2026-10-18** (the Mabit 632, the Alshich 630 and R. Shmuel de Uzeda 631, Russian and English each) were added at the TOP of the playlist, so every row moved by 6: the map was renumbered (including the `_left_out` keys) after checking that the old 724 videos are exactly the new rows 7-730, in order, with the same ids, durations, languages and titles, and rows 1-6 were mapped by their `defaultLanguage`. **A video's language is its own `defaultLanguage`, read through the YouTube Data API.** The playlist view translates titles to the viewer's language (yt-dlp, a browser and the oEmbed endpoint all show the English title of a Russian video), so two videos of a sage both look English there; the API's `snippet.title` and `snippet.defaultLanguage` are the original (`ru`, `en`, `iw` = Hebrew, which is how 359 / 352 / 19 of the 730 split). The owner listened to five pairs (Rashi, R. Jacob Landau, the Shach: Russian first; Rabbeinu Perachiah and the Meshech Chochmah: English first) and the field matched all five, and the order flips from pair to pair, so never infer a language from position, duration or title style (an earlier guess by position was wrong for 27 of 82 rows). `data/youtube-playlist.tsv` therefore holds the original title and language; refresh it with `python3 scripts/snapshot_youtube.py [--write]`, which needs the API key (the cloud environment's network secret adds it as `X-Goog-Api-Key` for `youtube.googleapis.com`; elsewhere set `$YOUTUBE_API_KEY`) and refuses to write when the rows moved, because `data/youtube-sage-map.json` is keyed by row. `defaultAudioLanguage` is `ru` on every upload (the channel's default), so it says nothing. The video pages and `www.youtube.com` itself still refuse the cloud sandbox (Google's "sorry" page). A video is only ever shown on the page of its own language (`lib/youtube.ts::sageVideos`). `components/sages/YoutubeWatch.tsx` is a click-to-load facade (nothing is requested from YouTube until the visitor presses play; the player is `youtube-nocookie.com`), used on the sage page (`#video`) and, for the site's introduction video (`INTRO_VIDEO` in `lib/youtube.ts`, empty until uploaded), on the About page. `tests/youtube.test.ts` fails when an id now belongs to another sage.

9. **Teacher, student and family links from Sefaria and Wikidata** (`public/data-catalog-links.json`, a generated supplement file merged over `data.json` on both paths, like `data-research-links.json`; never hand-edit it). `python3 scripts/build_catalog_links.py [--report]` reads Sefaria's topic links (taught / learned-from, parent / child / grandparent / ancestor / sibling / spouse / cousin / in-law, opposed, corresponded-with) and Wikidata's claims (student of P1066, student P802, father, mother, child, sibling, spouse, relative, influenced by) **between sages already on the roster**. Which Sefaria topic and Wikidata item is which sage is not decided there: it takes them from `data-sefaria.json` and `data-wikipedia.json`, and refuses to run when either has drifted from the roster labels. Direction follows the site's convention (`teacher` source = the teacher, `family` source = the elder relative). Checked like the spreadsheet's links but never flipped, and only on exact dates, since a century-precision sage's `birth_year` is the start of a window (the Rosh is 1200–1400): teacher younger than student dropped, lifetimes that never overlap or births over 90 years apart kept as influence, the catalogues or the site disagreeing on who taught whom dropped, a link the site already states not repeated, two book entries (`מחזור ויטרי`, `מדרש רבה`) never an end. Every decision is in `data/catalog_links_report.txt`. First run (2026-10-13): 128 links (95 teacher, 29 family, 2 influence, 2 colleague); teacher/student links on the site went from 31 to 126, family from 18 to 47, sages with no link at all from 110 to 98. Each entry stores both roster labels, and `tests/catalogLinks.test.ts` fails when an id now belongs to someone else. **`mergeDatasets` keeps one edge per relation**: a pair with a teacher, student or family link drops its influence link, and teacher X→Y with student Y→X is kept once, so the network graph does not draw two edges (or count a sage twice) for one relation; the sage page and the lineage tree already chose the strongest link per pair.

10. **Teacher and family links the research papers state** (`public/data-paper-links.json`, another generated supplement merged on both paths; never hand-edit it). Built by `python3 scripts/build_paper_links.py [--report] [--check]` from `data/links-from-research.json`, a reviewed list `{paper, a, b, a_label, b_label, type: teacher|family, relation, quote}`: on 2026-10-13 sub-agents read, in each paper, the sentences with a relation word (רבו, תלמידו, אביו, חתנו …) that name another roster sage, and recorded only what the paper states **for its own sage**: personal teaching (not learning from his books, not ordination, not "his school"), and family with `relation` naming a's role towards b, the elder first (father, grandfather, father-in-law, uncle, ancestor; brother, husband, cousin, brother-in-law, relative). Left out: what the paper doubts or calls a tradition it does not accept, namesakes (Aboab I is not Beirav's teacher), co-parents-in-law (מחותנים), relations inferred rather than stated, a book title in the sources list. Papers known to be about someone else (61, 81, 138, 192, 431) were not read. The build keeps an entry only while its quote is in the paper and both ids carry the labels they were read under, applies the same exact-date checks as the catalogue links (a teacher younger than his student is dropped, not flipped), and drops a relation another file states the other way round; a relation already on the site is not repeated. Every decision is in `data/paper_links_report.txt`. First run: 449 relations read, 211 links (128 teacher, 83 family); 2026-10-18 added one for the new 61 paper (61 is the father of 58), 212 links. With the catalogue links: links 492 → 682, teacher/student 31 → 254, family 18 → 130, sages with no link 110 → 82. **Fixed on the way:** `data.json` had R. Yaakov Margolis of Nuremberg (453) as the student of R. Yaakov Polak (457), an edge the rebuild recovers from `data.json.backup_v4`; both papers say the reverse (457: "רבו מובהק של פולק, רבי יעקב מרגליות מנירנברג"). The right link is now a curated one in `data-research-links.json`, so the rebuild drops the wrong edge (rule 4 above `TS = ...`) and its CSV influence twin, and both were taken out of the two copies of `data.json` to match what a rebuild writes.

11. **Sages added from the Chida's "Shem HaGedolim" and the owner's own material** (2026-10-18; ids 630-679; `data/shem-hagedolim-additions.json`, `tests/shemHagedolim.test.ts`). The owner asked to complete the corpus from Shem HaGedolim; a gap analysis (the Hebrew Wikipedia articles that cite the book, matched to the roster by name) listed the central sages the site lacks, and 50 were added: **the owner's own content first** (630 R. Moshe Alshich, 631 R. Shmuel de Uzeda, 632 the Mabit, 633 the Chizkuni: his Spotify episodes, and for 630-632 his videos; 630, 631 and 634 Rav Yosef Ba-Gad: his NotebookLM papers in Drive, with English and Russian translations), then 45 more from the Chida's list. Sefaria has only the book index ("מערכת ספרים", 2,022 entries), not the people index, so **the check** is that each of the 49 sages who belong to the book has a Maarekhet Sefarim entry that names him or his book, recorded with its ref and a verbatim quote; 634 is modern and not in the book. Where the book has no such entry the plan's reserve took the id: 663 R. Shmuel Abuhav (for Ezra of Girona), 664 R. Yonah Landsofer (for Azriel of Girona), 665 R. Netanel Weil (for R. Raphael Yosef Chazan), 666 R. Chiya Rofe (for Nehorai the Tanna), 678 R. Menachem Zioni (for Azariah de' Rossi). 671 is Moshe Galante the Second ("the Magen", 1620-1689), whom the book's entries are about, not the First.
   The method: **no invented facts**. Every sentence of a bio and of a core idea has a verbatim quote from a source that was really fetched (his Hebrew and English Wikipedia articles, his Sefaria topic, the Maarekhet Sefarim paragraph, the owner's paper); every year in a row occurs in a source text or is justified; where sources disagree on a year the row says the century or `כ־` and the record says why; the bio of a living man (634) leaves out a court case. ### The assistant (chat)

`POST /api/chat` answers with the language model (needs `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY` and the quota tables and RPCs in Supabase). The owner's plan: the model is switched on only when there is demand, funded by users (a symbolic payment towards the API, on top of the per-user quotas); until then the site answers automatically. **With no `ANTHROPIC_API_KEY` the route skips the auth and quota stores and answers automatically at once; and whenever the model path fails with a 5xx** (no key, no quota store, provider down or slow), the route answers anyway with the *automatic answer*: `lib/rag/referralAnswer.ts` is a **referral, not an answer, and not an apology**: it names the sage the question is about, says who he is in one sentence (the dataset's own summary in the question's language, never a quote of the research), cites the one research passage closest to the question (a handle the widget numbers and links to its heading), and returns `links` (his page, the research, the episode, the video of that language, the writings, up to three relatives) that `ChatWidget` shows as "go further" chips; only sections the page really has get a chip. It never says the assistant is unavailable (the owner asked for that). The response carries `mode: 'referral'`, costs nothing and is not counted against the quota. A name that fits several sages gets a chip for each page; a question naming nobody says so. 4xx (a spent quota, an invalid session) are not turned into answers. Don't turn a model failure back into a bare 500: on 2026-10-11 production returned `500 internal_error` for every question (the quota-check `GET` still answered 200, so the widget looked healthy) and the cause was only visible in the Vercel runtime logs. The search box offers the assistant as its own row (`SearchBar` → `askQuestion()` in `components/chat/askAbout.ts` → `ChatWidget` opens unscoped and sends it); a text that reads as a question (`looksLikeQuestion`) puts that row first. Sages are matched in the question by their Hebrew name and, through `lib/rag/buildContext.ts::localNamesFor`, by the English/Russian overlay label (a Russian name also with a case ending). A name inside a longer name the question holds is not a mention of its own ("Shmuel HaNagid" is not also Shmuel the Amora), epithets ("King", "prophetess", "царь") are not names, and among the sages found by a single word, the one more of whose name the question holds comes first (the first sage is the one the answer leads with). `tests/automaticAnswer.test.ts` covers all of it.

Safari on iOS has no prompt: the button (mobile menu, About page) shows the "Share → Add to Home Screen" steps instead, and the desktop header hides it there. Nothing is shown once installed. Where it sits: header (desktop, icon only), the mobile ⋯ menu, the About page.

It registers in production only (in development it would serve stale files). To drop everything every visitor holds, bump `VERSION` in `sw.js`. A change to what the worker caches needs a test: a worker that caches the wrong thing breaks the live site quietly, and only for returning visitors.
- **Not done on purpose**: no push notifications (iOS needs a Home Screen install first, and nothing here has a reason to notify yet), no Capacitor/store wrapper (decide from the numbers above; Apple's guideline 4.2 rejects a thin web wrapper, so a store app would need native value: sage of the day, offline reading, sharing).

### The sage riddle ("חידת החכם", `/[locale]/riddle`, added 2026-10-14)

A daily game, Wordle-style, and a reason to come back (it feeds the "~25% returning within a month" question above): **one hidden sage a day, the same for every visitor**, found from clues that come one at a time; each wrong guess unlocks the next clue and says how the hidden sage stands to the guess. Six guesses. The result is shared as a grid of emoji that does not give him away; a streak and statistics are kept in the browser.

- **Files.** `lib/riddle.ts` is **pure and also bundled for the browser** (scoring, share text, storage rules): it imports no overlay and no dataset, so the server hands it already-localized sages through a `RiddleContext` (`byId`, `LinkIndex`, `localize`). `lib/riddleServer.ts` builds the context from the corpus, the pool, today's pick and the page's payload. `app/[locale]/riddle/page.tsx` (`revalidate = 1800`, he/en/ru, `/xx/riddle` is a 404 after the middleware's redirect like every unknown locale) and `components/riddle/RiddleGame.tsx` (the client game). `tests/riddle.test.ts` runs on the real corpus.
- **Day and number.** `dayNumber` (Israel midnight, `lib/today.ts`); `riddleNumber = day - RIDDLE_EPOCH + 1`, #1 is 15 October 2026; before it the number is 0 or less and the page and the share text simply leave it out. The countdown to the next riddle is `nextRiddleAt` (a bisection on `dayNumber`, so a clock change is no problem).
- **The pool** (`riddlePool`): a research paper, a name in English and Russian, a known era, place (one that maps to a region through `regionsOf`: without it the region hint would be a guess), field and core idea, at least one teacher, student or family link to another roster sage, at least 4 clues in every language, and **a fame of at least `MIN_FAME` = 8** (a daily game whose answer most players never heard of loses them in days; without this rule the pool was 266 and the first two weeks were Shimon ben Shetach, R. Avraham Cohen de Herrera, the Maharil Diskin…). `fameScore` (in `lib/riddle.ts`, pure) is the sage's distinct link neighbours on the roster (`LinkIndex.degree`, every link type), **+3** for a Hebrew Wikipedia article, **+2** for an English one, **+ min(works Sefaria lists for him, 5)**; `lib/riddleServer.ts` reads the files (`wikiLinks()` of `lib/wikipedia.ts`, which prefers Wikidata and falls back to the titles Sefaria holds, and `getSefaria().total`) and passes `fame` in on the `RiddleContext`. **136 sages on 2026-10-14** (146 on 2026-10-18, with the 50 from Shem HaGedolim) (Rashi, the Rambam, the Ramban and R. Akiva are in; R. Avraham Cohen de Herrera and R. Yaakov ben Chananel Sikili are out; the test finds them by label, never by id). The pick (`riddleIdOn`) is `sageOfTheDay` over that pool, so every pool sage comes once a cycle; it **never lands on the Today page's featured sage of the same day** (`todayFeature`): on a clash it takes the next sage of the pool in id order (1 clash in 1100 days, so the cycle is only rarely disturbed). Adding a sage to the pool, or changing who has a link, an article or a Sefaria entry, shifts every later day's riddle: that is as it is on the Today page.
- **Clues** (`riddleClues`), vague to specific, at most 6, each `{ kind, label, text }`: era, field, place, years (or the century), one relative (a teacher, else a student, else family: the link direction is the usual one, `teacher` source = the teacher, `student` source = the student; the best-connected one is named), the core idea. Place and field are shown through the same translated labels as everywhere (`location_label` / `field_label`), the logic reads the Hebrew. **No clue holds the answer's own name:** the core idea has it replaced by "…" (`nameVariants` / `maskName`: the roster label and the language's label, whole and by the pieces outside and inside its brackets, without the title (רבי, Rabbi, Рабби) and, for an acronym, without the article; quotes written either way; a three-letter name only as a whole word; Russian case endings), and any other clue that holds it is left out (the era is exempt: it is one of eleven fixed labels). The roster's labels use an ASCII `"` in acronyms where the text uses gershayim; both are matched.
- **Feedback** (`compareGuess(guess, answer, linkedIds)`): era of the answer relative to the guess (`earlier` / `same` / `later`; within one period by `chronoYear`, only when both are dated and more than 50 years apart). The chips say just "Later" / "Earlier" / "Same era" (he: מאוחר יותר / מוקדם יותר / אותה תקופה): "later era" would be false for two sages of one era 50+ years apart, and a verb ("lived", "חי", "жил") would give away the hidden sage's gender; region (`same` / `other`, **`unknown` when either place maps to no region**: 31 roster places, such as Posen, do not, and "other region" would be a false statement), and `linked` (direct teacher, student, family or colleague link). The candidate list the page ships (`{ id, name, period, regions (bit mask), year, linked }` for every roster sage; the whole payload was about 50 KB for Hebrew (56 KB since the roster grew to 509 sages; the test's ceiling is 68 KB)) holds no bios; the **answer's id is in the payload** (no server-side checking: it is a game, not a vault). The autocomplete is `searchSagesRanked` over those names (nikud, gershayim and final letters forgiven); a sage cannot be guessed twice; a pick from the list is confirmed with the button (Enter submits at once), so a stray tap does not spend one of six guesses. The list opens above the field when the visible screen leaves more room there (a phone's keyboard).
- **Share** (`shareText`): `חידת החכם #12 🧩 4/6`, then one row per guess (era 🟩 same / 🔼 later / 🔽 earlier, region 🟩 same / ⬜ other or unknown, 🔥 linked), 🎯 for the winning guess, `X/6` on a loss, and the link. Never a name or id (a test checks the shape over the whole pool in three languages). Web Share, else the clipboard (the sage page's `copyText` and toast), and a `wa.me` link.
- **Storage** (`ozar-riddle`, localStorage only, every access in try/catch; a blocked storage means a game without a record): `{ day, guesses, done, won, stats: { played, won, streak, maxStreak, dist[6], lastDay, lastWon } }` (`lastDay` / `lastWon` are what the streak rule needs). `parseState` repairs or discards anything unreadable; a new day starts a new game and keeps the stats; **the streak lives on only if the last finished game was yesterday's and won** (`currentStreak`). The game follows the payload's day, not the browser's clock: the page is rebuilt every 30 minutes, so for up to half an hour after Israel midnight a visitor may still be given yesterday's riddle (the countdown's end offers a reload); a browser that already holds a newer day than the page it was handed (a stale cached page) is told to reload and nothing it holds is overwritten.
- **End screen**: the sage (name, years, era, a bio cut at a sentence end), his page, his place in the Tower (`towerPath`), his quiz when the language has one, the share block, the statistics with the distribution of wins, and the countdown. Entry points: 🧩 in the desktop header (**from 768px up**: between 640 and 768 the header row has no room for another icon, at exactly 640px the English header already overflows by 41 px without one) and an item in the mobile ⋯ menu; a card on the Today page (a plain `<a>`, not `next/link`, which would prefetch the ~50 KB payload for every Today visitor); `/riddle` in the sitemap in three languages. Not done: accounts, leaderboards, a per-riddle share image, server-side answer checking.

### Six Steps ("שישה צעדים", `/[locale]/connect`, added 2026-10-14)

The links the site collected (682 between roster sages) made to be felt: pick **any two sages** and the site finds the shortest chain of recorded relations between them and **flies it in the Tower of Generations**, a line on every link ("תלמידו של רש״י"); and a **daily game**, "שרשרת החכמים" (Sage Chain), connects two sages by naming linked sages one at a time. The page is rebuilt every 30 minutes like the riddle and holds the game above the picker; entry points below.

- **Files.** `lib/connect.ts` (pure, also bundled for the browser: graph, search, captions, the `ConnectNet` payload), `lib/connectServer.ts` (graph over `getAllSages()`/`getAllConnections()`, `connectNet(locale)`, `connectPathFor(locale, from, to)`), `lib/connectFlight.ts` (pure: `buildFlight`, `flightHref`, `connectHref`), `lib/chain.ts` (pure: the game's rules, storage and share text), `lib/chainServer.ts` (candidate pairs, the pair of the day, the page payload), `components/connect/` (`ConnectPicker`, `ChainGame`, `SageCombobox`, `FlightPanel`), `app/[locale]/connect/page.tsx`, `app/[locale]/tower/path/[from]/[to]/page.tsx`. Tests: `tests/connect.test.ts` (graph, path, captions, net size), `chain.test.ts` (rules on synthetic worlds), `connectFlight.test.ts`, `chainServer.test.ts` (the corpus: 400 days), `connectPages.test.ts` (entry points, pages, analytics, this file).
- **The graph.** One edge per pair of roster sages, the strongest kind the data holds (teacher > family > predecessor > colleague > oppose > influence); a `student` link is stored as `teacher` the other way round; `contemporary`, self links and links to ids off the roster are not relations. **Search** is Dijkstra over the kinds' weights (teacher 1, family 2, predecessor 2, colleague 2.5, oppose 3, influence 4: a route of teachers beats a route of inspirations) and ties go to fewer links. A path is computed from the end that comes first in id order and reversed for the other, so b→a is a→b read backwards, ties included. On 2026-10-14: 636 links among 376 sages that have one; 95 components, the largest 327 of 459 sages, 83 sages alone; Rashi→the Rambam is 2 links (Rashi influenced Bachya ben Asher, a disputant of the Rambam).
- **Captions: the direction rule.** `PathStep.via = { kind, dir }` says how a sage is linked to the **previous** one: `dir` is `up` when the previous sage is his teacher / elder relative / predecessor / influencer, `down` for the reverse, `none` for colleague and disputant. `stepCaption(via, prevName, locale, feminine)` reads that and nothing else: teacher↑ "תלמידו של X / Student of X / Учился у: X", teacher↓ "רבו של X", family either way "בן משפחתו של X / Relative of X" (the data does not say son or grandson), predecessor↑ "ממשיכו של" / ↓ "קודמו של", influence↑ "הושפע מ־X" / ↓ "השפיע על X", colleague "חברו של", oppose "בר־פלוגתא של". Hebrew agrees with the sage described (the `נשים` tag; a woman the tag misses is described as a man, as six were until 2026-10-25). The stored direction is followed, not reoriented by chronology (about 16 of 580 dated directed links have the upper end born 25+ years after the lower). `tests/connect.test.ts` parses 50 sampled paths' captions back to (kind, dir) in all three languages and compares them with the stored source/target.
- **The payload.** `ConnectNet` is compact tuples, `sages: [id, shortName, periodIndex, woman?]` and `edges: [a, b, kindIndex]` (indices into `sages`), only sages with a link; the picker and the game both build their graph from it (`graphFromNet`). **Budget: under 25 KB for Hebrew** (28 KB since 2026-10-18: the 50 added sages took the Hebrew net to 25.5 KB) together with the day's payload: on 2026-10-14 he 22.8 KB + 0.3 KB, en 20.1 KB, ru 25.6 KB (the Russian net alone is over: Russian names are longer; the criterion names Hebrew). Names are short names (no epithet), so the roster's ASCII `"` in acronyms shows as it does on the riddle page.
- **The flight** (`TowerScene` has a `flight` prop beside `tour`, handled at every `tour`/`tourRef` site: no choosing sages, the address untouched, the time-lapse controls hidden): the trail is **teal** (`FLIGHT_COLOR`, apart from the road to Sinai's gold and the kids' tours' gold and rose), **dotted** where the link into the next sage is influence, one numbered label per station; it plays by itself once the scene is built (2.4 s a station), holds 2.6 s at the end and pulls back over the whole thread (on a phone its card covers more than half the screen, so `roadOverview` stands 1.45× farther back and aims a span lower for a flight; the road to Sinai's overview is unchanged). `FlightPanel`: "תחנה i מתוך n", the sage's name (his page), era chip, years, the caption; prev/play/next; at the end "n steps between A and B", the overview, again, share (Web Share, else the clipboard, the flight's own address; event `tower_share`) and a link back to `/connect?from=&to=`. `/[locale]/tower/path/<from>/<to>` is made on first request (`generateStaticParams` none), `noindex`, 404 for an unknown id, the same sage twice or two sages with no path; the title is "A ← B" (Hebrew) / "A → B". `?via=picker|game` says where the visitor came from (event `connect_fly`; anything else is `link`); the share address drops it. The chosen sage's panel in the tower links to `/connect?from=<id>`.
- **The game** (`lib/chain.ts`): the chain starts at A and the player names a sage; one **directly linked** (any kind) to the chain's current end joins it (with the link's caption), otherwise it is a miss; reaching B wins; **5 misses lose**. A sage already on the chain, or already named since the last hit, is refused at no cost. Misses are forgotten at a hit (a sage not linked to the old end may be linked to the new one) but `misses` counts them. Hints: the number of the end's direct links is always shown; from the **2nd miss** the era and from the **4th** the field of the first sage strictly between A and B on the optimal route who is not yet on the chain (`chainHints`; the field text is `ChainDay.fields`, the era comes from the net). Score = steps taken over the best (`4/3`). **Call `startChainDay(state, day, a)` before `applyMove`**: `applyMove` refuses a state that is not this day's game. The end screen shows the optimal chain, the way into the tower and the share block.
- **The pair of the day.** `chainCandidates()`: pairs a<b of the **riddle's fame pool** (136 sages, `riddlePoolIds()`) whose **fewest links** (BFS) are 3 to 5 **and whose cheapest chain (the one the tower flies and the end screen shows) has the same number of links**, so the game's "best" and the picker's chain agree: 2,405 pairs on 2026-10-14 (885 / 905 / 615 for 3 / 4 / 5); 2,816 on 2026-10-18. `dailyPair`: sorted by (a, b), `sageOfTheDay` over the positions, so every pair comes once a cycle (about 6.6 years), the same for every visitor; it **never holds the riddle's answer of the same day** (on a clash the next pair that holds neither end; 5 clashes in 400 days). #1 is 15 October 2026, like the riddle, and the day turns at midnight in Israel. Adding a sage to the pool, or a link that changes a distance, shifts every later day.
- **Storage** (`ozar-chain`, localStorage only, every access in try/catch): `{ day, chain, misses, missed, moves, done, won, stats }` (`moves` is one letter per move, `h` hit / `m` miss, what the share row is drawn from; `missed` the sages named since the last hit). `parseChainState` repairs or discards anything unreadable; a new day starts at A and keeps the stats; the streak lives on only if the last finished game was yesterday's and won (as the riddle); a browser that already holds a newer day than the page is told to reload and nothing is overwritten.
- **Share** (`chainShareText`): `שרשרת החכמים #3 🔗 4/3` (a loss `✗/3`), one row with an emoji per move (🟩 hit, ⬜ miss, 🎯 for the hit that reached B) and the link. Never a name or an id (checked over 200 days × 3 languages).
- **Entry points.** The ⋯ menu on phones (no desktop icon: the row between 640 and 768 px is full), the About page's "ועוד" list, the sage page ("המסלול אל חכם אחר", a plain `<a>` to `/connect?from=<id>`, beside the tower link), the tower's chosen-sage panel, the riddle's end screen ("משחק נוסף: שרשרת החכמים"), `/connect` in the sitemap in three languages (the path pages are not). The language links of the top bar on `/connect` do not carry `?from=&to=`: `followUrl` follows the pathname only, which does not change here.
- **Share images of a path** (2026-10-18). `/<locale>/tower/path/<from>/<to>/opengraph-image` is the link preview (1200 x 630 PNG, 168 to 179 KB for Rashi to the Rambam; the test's worst case 237 KB, the ceiling 270): the title, the step count, and the stations as round faces joined by a teal line (dotted where the link is influence, an arrowhead the way the line reads), the short name under each. `/story` is the status image (1080 x 1920, the file for the share sheet): faces of 150 to 220 px down the image, each station's name, era and years, and between two stations the caption of the link, as the flight panel says it, and the path's address. More than 7 stations (the card) or the story's limit: the first 3, a dashed "+k" disc and the last 3 (`elide`; the step count is always the real one; the longest path in the graph on 2026-10-18 is 17 steps, `346` to `502`). Both are drawn by `lib/pathShare.ts` (data, titles, layouts) and `lib/pathShareArt.tsx` (the Satori pieces), 404 for an unknown sage, the same sage twice or no path, `Cache-Control: public, max-age=3600, s-maxage=86400`, and both routes are traced in `next.config.ts`. Portraits come from `lib/ogPortrait.ts` (JPEG) only; a station with none is a disc in its era colour with the medallion. **The card's PNG size is set by the painted faces**: `CARD_FACE_AREA` caps their total area (about 2.8 bytes a pixel for a photograph), so more faces are smaller; `tests/pathShare.test.ts` renders, for each length, the path with the heaviest JPEGs in three languages. Credits: one line per kind of portrait drawn, from `ogCaption`; when a path has both photographs and illustrations the photographs carry a small camera mark and so does their credit line. Hebrew names and captions go through `gershayim()` (the roster's ASCII `"` in acronyms becomes ״). Satori limits met here: no CSS-border triangles (they draw as squares), no emoji, `●` is missing from all four fonts, a long word is never broken (`wordFit` shrinks the type), so arrowheads, dotted lines and the dashed ring are inline SVG. The path page's own metadata names the card as `og:image` and `twitter:image` (`summary_large_image`); `titleOf` lives in `lib/pathShare.ts`. **The button** "📸 תמונה לשיתוף" (`components/connect/SharePathImage.tsx`, at the end of the flight panel and in the picker's result, so a path can be shared without flying it) fetches the story image and shares it as a file (`lib/shareFile.ts::shareImageFile`: Web Share with files, else a download, else the image opens in a tab); events `tower_share` with `method: 'image'` or `'download'`.

### Tower of Generations (`/[locale]/tower`, added 2026-10-14)

The whole corpus in 3D: **height is time** (piecewise, so the full centuries get the height: `lib/tower.ts::heightOf`), **direction is region** (ten sectors around the axis, map neighbours next to each other: Eretz Israel, Middle East, North Africa, Sepharad, Provence, France, Italy, Ashkenaz, Eastern Europe, other), and a cone that widens with time. Teacher links are golden arcs with light running from teacher to student, family links rose, influence (off by default) faint. Press a sage: his teachers' teachers and students' students (four steps) and his family light up, the rest dims, the camera flies to him and a panel lists them with a link to his page. Play runs the 3,700 years in ~30 s (sages and links appear when they have lived; a slider scrubs). Undated sages stand at their era's middle, placeless ones at their era's centre of Torah (Eretz Israel, then Babylon).
- `lib/tower.ts` (pure, `tests/tower.test.ts`): `buildTower` (positions, sizes by degree, era colours, the 16 most connected as named landmarks, short names without epithets), `lineageOf`. Deterministic: a sage keeps his place from build to build.
- `app/[locale]/tower/page.tsx` computes the layout on the server and ships positions and names only; `components/tower/TowerScene.tsx` draws it with three.js (`three` pinned, **imported dynamically inside the effect**, so no other page loads it; the test checks there is no top-level import). Names are DOM labels (`CSS2DRenderer`), so Hebrew renders natively: their container is `dir="ltr"` because CSS2DRenderer positions from the left edge, and `z-index: 0` so the panel and controls stay above the labels' own z-indexes. Styles `.tower-*` in `globals.css`; on phones only the first eight landmark names show and the camera aims lower so the tower clears the controls. No WebGL: a message and a link to the network.
- Entry points: 🌌 in the desktop header and an item in the mobile ⋯ menu; in the sitemap in all three languages.
- **Faces** (2026-10-18): a sage with a portrait (`node.face`, his tile in the atlas that `lib/towerServer.ts` ships as `data.faces`, via the pure `lib/towerFaces.ts::attachFaces`; `buildTower` is untouched) is a round camera-facing face with a ring in his era's colour, not a sphere, so the tower is a wall of faces across 3,700 years. `components/tower/faceLayer.ts` draws them all as one `THREE.Points` with a shader (one draw call); it imports only types from three (the scene hands the module in), and the pure parts (tile geometry, sizes, picking, the grow's timing, the shader source) are exported for `tests/towerFaces.test.ts`, which runs without WebGL. **The atlas loads after the scene is built**; a sage's sphere and halo are hidden only once it has loaded, so a failed or blocked fetch leaves the tower as it was, with nothing shown or thrown (checked with the request aborted and answered 404). Face size is `state scale x clamp(world / depth, floor 20, cap 60)` CSS px (a host under 640 px wide: 16 and 44), clamped to the GPU's point-size limit (the circle stays a circle there); states as for spheres: dimmed 0.5 and darkened, chosen 1.35, chain 1.15, hidden by the time-lapse. Dimmed faces and the spheres of sages without a portrait are dark, so **while anything is dimmed the faces that are not dimmed are drawn `FOCUS_PULL` (40 units) nearer along the view ray, for the depth test only**: a dimmed sage standing between the camera and a station used to show as a dark disc over the station's face. Halos are dropped under faces (an additive halo at the same depth washed the face out). **Picking is on the screen, by what is drawn**: the faces are ranked by the depth the shader draws them at (`drawnDepth`: the true depth; `FOCUS_PULL` nearer for a face that is not dimmed while something is; a face in a sharp slot, the grown one, in front of everything inside its disc), so the front-most drawn face whose disc holds the point wins (the nearer centre at equal depth), else the nearest centre within a slop of 3, 8 or 14 px for mouse, pen or touch; it is merged with the sphere raycast by the distance as drawn (`drawnDistance`; spheres are drawn at their true one, so a sphere in front of a face wins, a grown face beats any sphere). Ranking by the true depth was a bug: in a chosen sage's view a click on a lit chain face, or on the chosen sage's own grown face, selected a dimmed sage standing nearer but drawn behind it (10 of 24 clicks inside the grown disc stayed on the sage, now 24 of 24, on both viewports). Every isolated face was hit by its centre, 30 of 30 with a mouse and 30 of 30 with a touch, and a face behind another is not picked, as it is not seen. **The face at a station grows toward the screen**: on a road to Sinai, a kids' tour or a Six Steps flight, and for the chosen sage, the face eases from 1 to 2.6x in 600 ms (instantly under `prefers-reduced-motion`), the previous one eases back and `roadOverview` returns all; while grown it is drawn sharp from the sage's own 128 px file (a single-point layer, blended, `depthTest` off, loaded on demand, the atlas tile until then), the sage's name stands above it (`.tower-label-grown`) and, at 96 px or more, **the episode credit stands under it** (`.tower-face-credit`, the text from `portraitCredit`: the site's rule that a portrait of 96 px or more carries its credit). **While a face is grown, the names that would lie over it are hidden** (`hideUnderFace` in `TowerScene.tsx`: every other sage's name, a flight's station numbers, the era and region names, the hover name, and whatever would sit on the credit line; a name is a box whose width is estimated from its length, no layout read, hidden by `visibility` when it comes within 14 px of the disc by the pure `labelCovered`; the grown sage's own name stays; restored when no face is grown, and recomputed only when the disc, the camera or the set of names changed). In `TowerScene.tsx` the word "portrait" stays inside `PanelName`; the scene says "face" (`tests/portraitsTower.test.ts` fails on any other line). Browser checks: `host.towerFaceAt(id)` gives `{x, y, r}` of a face on the canvas and `data-tower-faces="<count>"` is on the host once the layer is on; both are inert in production. The tower page's data grows by 3,630 bytes (he 196,612 to 200,242 as JSON; 196,708 to 200,338 since 2026-10-25, when six more nodes got `feminine: true`); the home page's bundle is unchanged (the atlas address is only in the tower pages' data). Frame times could not be measured meaningfully: headless Chromium here draws with software GL at about 4 frames a second and the base and the new build were within the noise (240 and 229 ms mean on desktop, 231 and 237 on the phone viewport), so the cost on a real GPU is by construction (one draw call, nothing per frame at rest, no allocation in the frame loop) and not by measurement.
- **Flights**: `TowerScene` has a `flight` prop beside `tour` (a path between two sages, teal, dotted for influence; "Six Steps" below), both handled where the scene checks `tourRef`/`flightRef`, and a link in the chosen sage's panel to `/connect?from=<id>`. Pages that fly something (`/kids/journey/<route>`, `/tower/path/<from>/<to>`) mount `TowerScene` themselves, not through `TowerPage`.
- **Opened on a sage** (`/[locale]/tower/<id>`, `app/[locale]/tower/[id]/page.tsx`): the tower with that sage already chosen and his chain lit, the camera flying to him. Every sage page links there ("הצגה במגדל הדורות", a plain `<a>`, so the sage page does not prefetch the whole tower). The scene keeps the address on the chosen sage (`history.replaceState(null, …)`: with Next.js's own state instead of `null`, `usePathname` is not told, and the top bar's language links, `LocaleLinks` with `followUrl`, would point at the old sage), so a copied or shared link (the panel's "שיתוף" button: the share sheet, else the clipboard; event `tower_share` `{locale, method}`) opens on the same sage, and its preview is that sage's share card. Each page is made on first request and cached (`generateStaticParams` returns none), is `noindex` (only `/tower` is in the sitemap), and an id that is not a sage is a 404. The scene is built after three.js loads, later than the effects that pass it state, so it reads the current state (`live`) once built.

### The road to Sinai ("הדרך לסיני", added 2026-09-27; flown in the tower since 2026-10-14)

From any sage back to Moses at Sinai, in two parts kept apart because they rest on different authority (`lib/sinaiPath.ts`, pure). **The chain**: `lib/sinaiChain.ts::SINAI_CHAIN`, the forty generations of the Rambam's introduction to the Mishneh Torah (Moses = 1 … Rav Ashi = 40, through the Nesi'im, with those he names receiving alongside as `alongside`), continued as gens 41–45 by Iggeret Rav Sherira Gaon (Ravina and the close of the Talmud, the Savoraim, the Geonim, Rav Sherira, Rav Hai); its people are matched to the corpus **by Hebrew label, never by id**. **Below it**: the archive's own lineage links, chosen by a weighted search (`buildSinaiIndex`: teacher 1, succession 2, family 2.5, influence 4 plus a cost per century leapt), so a route of teachers beats a route of inspirations; nothing is added that the data does not hold. On 2026-10-14: 239 of 459 sages have a road, 37 of them on teacher links alone; Rashi has none (the Ashkenazi chain stops at Rabbeinu Gershom), and `sinaiTrail` shows how far back his record does go.
- Where it shows: the sage page's card (`components/viz/SinaiPathCard.tsx`, server-rendered), the full "river" in the lineage tab (`?tab=genealogy&view=sinai&focus=<id>`, `components/viz/SinaiPath.tsx`), and the Tower of Generations (below). Strings shared by all in `components/viz/SinaiPathText.tsx`.
- **In the tower**: `lib/towerServer.ts` adds `road` to the tower data (`lib/tower.ts::buildTowerRoad`: each sage's next step up and the chain's stations, ~12 KB), `roadOf(data, id)` walks it (the sage first, Moses last; `tests/tower.test.ts` checks it equals `sinaiPath` for every sage). A station nobody in the corpus stands for (Joshua, Eli, Elijah…) is drawn between its neighbours on the road, never given a date. The chosen sage's panel has a "הדרך לסיני" button; the camera then flies down the centuries station by station (`SceneApi.road` / `roadGo`), a golden thread unrolling behind it (solid for teacher and chain, dotted for inspiration), a caption per station (name; years, except under a group station; how he received from the one above, from the Rambam / Rav Sherira or the archive's link), and at Sinai pulls back to the whole thread, with the honesty note, sharing and "again". `?road=1` in the address starts it, so the card's "המסע במגדל הדורות" link and a shared road fly it at once. ### The sage quiz

A "get to know the sage" quiz on the sage page (`components/sages/SageQuiz.tsx`, section `#quiz` after the research, plus a "חידון" chip in the page header). The game itself is `components/quiz/QuizPlayer.tsx`, shared with the kids' station quizzes (below): length, progress store, wording and the `kind` (`sage` | `kids`) carried on the events are its props. Twenty questions drawn from the sage's research paper, one at a time, each answered with a short explanation; 100 points in all; 0–3 stars at 50 / 75 / 90 (`lib/quiz.ts::STAR_THRESHOLDS`). The owner asked for the schema of a school quiz importer, kept exactly: each question is `{ question, options, correctIndex, explanation, points }`, and two options make a true/false question (kept in order, "true" first; multiple-choice options are reshuffled every game by `shuffleForPlay`). Nothing is fetched until the visitor starts. The best result per sage stays in the browser only (`lib/quizProgress.ts`, localStorage `ozar-quiz-progress`): that is the "journey passport", counted on the result screen. Events `quiz_start` and `quiz_complete` (`{locale, kind, score, stars}`).

- **Files**: `public/quiz/<id>.json` (Hebrew), `<id>.en.json`, `<id>.ru.json`, each `{ label, questions }`. `public/data-quiz.json` is the index the server bundles to decide whether a page has a quiz in its language (a quiz is never shown in another language). Another per-id side file: the label guards against ids drifting, and `tests/quiz.test.ts` fails when an id now belongs to another sage, when a file breaks a rule, or when the index and the files disagree. Never hand-edit a quiz's id or label; regenerate. The English and Russian quizzes of the 22 sages that have a Hebrew quiz are translations of the Hebrew quiz (`scripts/translate_lines/tx_quiz.py`): same questions, `correctIndex`, `points` and label (the Hebrew roster label in every language), names as in that sage's research translation; a sage without a Hebrew quiz has none in en/ru either.
- **Rules** (`lib/quiz.ts::validateQuiz`, mirrored in `scripts/build_quiz.py::validate`): exactly 20 questions (10 for a kids' station quiz: `validateQuiz(quiz, KIDS_QUIZ_LENGTH)`), 2 to 4 distinct options, a `correctIndex` that is an option, an explanation, positive whole points adding up to exactly 100.
- **Generation**: `scripts/build_quiz.py` sends the research paper (citation markers and the closing source list stripped; a dash line is often only a section break, so only a final section of links is cut, and a document stored twice is sent once) to the Claude API as a Message Batch, with the prompt in `scripts/quiz_prompt.md` (adapted from the owner's school prompt: 6 true/false, 10 medium and 4 hard multiple-choice, answerable from the paper alone, doubtful claims left out, explanations in the paper's terms, Hebrew with proper gershayim). The model marks each question easy/medium/hard; the script assigns 3/5/8 points scaled to exactly 100, so the model never does the arithmetic. `--submit` (records the batch in `data/quiz-batches.json`), `--collect <batch>` (writes, validates, reports the failures to resubmit), `--index` (no API: validates every file and rebuilds the index), `--dry-run`. `--lang en|ru` writes the quiz in that language from the Hebrew paper. It needs an API key, which the cloud environment does not have; a full Hebrew run is ~445 papers.
- **Written in session so far (22)**: the pilot, the Rambam (41), Rashi (594) and Dunash ben Labrat (198), to settle the format before a full run; then every other sage a kids' station links to (592, 507, 346, 437, 573, 585, 72, 428, 130, 143, 156, 629, 389, 282, 556, 534, 524, 510, 496), so a child who follows a station's link finds a quiz there. All were written from the paper as `research_text()` sends it, under the same prompt (the 6/10/4 mix, about three true and three false, the right answer's position spread over the four options, claims the paper itself hedges or that look doubtful left out) and through the same `to_quiz` path. Their style is what the batch will reproduce: review them before generating the rest.
- The service worker keeps quizzes in the research cache, so a quiz once played can be played again offline.

### Client data loading: static pipeline only

`AppShell.tsx`'s bootstrap calls `loadAppShellData()`, which fetches `data.json`, the supplements and `data-patch.json` in parallel and merges them with the same `mergeDatasets`/`applyPatches` the server uses, so the home page and the sage pages always show the same corpus. It does **not** read Supabase. It used to fetch Supabase first (`sages_with_stats` / `connections_with_names`) and prefer it whenever it held ≥300 sages and ≥100 links. That made every visitor wait on Supabase, with no timeout, before anything rendered. And because production Supabase holds an old snapshot (missing ~100 current sages such as Rashi, and carrying links deleted since), that stale data won. Don't reintroduce a Supabase read for the public graph. Supabase is a separate, independently populated store, used for auth, chat and the personal area. Search doesn't touch it either: `SearchBar` ranks the loaded sages with `lib/search.ts::searchSagesRanked` and, in the moment before the static data arrives, shows a loading state (the old Supabase `searchSages` fallback is gone). The home page's initial header count and About stats come from `lib/serverData.ts::getCorpusStats()` at build time.

The individual sage page (`app/[locale]/sage/[id]/page.tsx`) is server-rendered and reads **only** `data.json` via `lib/serverData.ts` (bundled at build time, not fetched over HTTP — `public/` isn't readable via `fs` in Vercel's serverless functions). It never touches Supabase.

### Visualization tabs

`AppShell.tsx` orchestrates seven tabs (`Tab` type in `lib/types.ts`): network graph, geography map, traditions, table, timeline, genealogy tree, about. Two different mounting strategies are in play — worth knowing before debugging a "tab shows nothing" report:
- **Graph and map tabs stay mounted permanently**, just toggled via a `hidden`/`block` CSS class, so their data-loading `useEffect`s fire once on initial app load regardless of which tab is active.
- **Traditions, timeline, table, genealogy, about are conditionally rendered** (`{activeTab === 'x' && <Component/>}`) — they mount fresh each time the user switches to them.

`GeoMap.tsx` (Leaflet) depends on its container having non-zero size at init; because it's always-mounted it can initialize while `display:none`, so it explicitly calls `map.invalidateSize()` on an `activeTab`-change effect to recover. `NetworkGraph.tsx` runs d3-force on its own internal timer and renders from `sim.on('tick', …)`. If you ever switch it to manual stepping, remember that d3-force only dispatches `'tick'` when its own timer runs, **not** on manual `.tick()` calls, so the per-tick DOM update must then be called directly. `GenealogyTree.tsx` runs no simulation (it used to: a force layout of every sage in era bands). It is a lineage explorer centred on one focus sage: the pure module `components/viz/lineage.ts` orients the lineage links (teacher/student, influence, predecessor, family) upper → lower, draws a link stored against the chronology in date order, builds the tree a generation at a time up and down (a sage reached twice is drawn once and then as a repeat reference, so cycles end), and lays it out as a tidy top-down tree or, below 700px, an indented outline. The component only joins, transitions and zooms with d3.

Single Zustand store (`store/useAppStore.ts`): sages/connections/sageMap, selection, active tab, theme (persisted to `localStorage`), and filter state (period/region/field/free-text search via `lib/search.ts`'s Hebrew-aware fuzzy matcher — nikud/gershayim/final-letter insensitive). Pinned by name (ids drift, names do not) in `tests/tower.test.ts`, `tests/connect.test.ts` and `tests/descriptionLinks.test.ts`, and **guarded by a rule**: `tests/terms.test.ts` fails when a sage's tags hold the word נשים inside a longer tag (`נשים בתלמוד`, `מעמד נשים`) without also holding the whole tag. A new woman needs the whole tag `נשים` in the spreadsheet's tags cell and in both copies of `data.json`. A search of all 509 labels on 2026-10-25 found no other woman without it.
- **Period keys**: `patriarchs, exodus, judges, kings, second-temple, tannaim, amoraim, geonim, rishonim, acharonim, modern` (`lib/types.ts::ALL_PERIODS`, chronological order — this order drives the timeline band layout, and orients lineage links between undated sages in the genealogy tree).
- **Connection types**: `student, teacher, colleague, influence, oppose, predecessor, contemporary, family`.
  Direction matters for the two lineage types: `teacher` means **source is the teacher of target**, `student` means **source is the student of target**. Any UI that labels a related sage ("רבו" / "תלמידו") must look at which end of the link the current sage is on. `rebuild_data_from_csv.py` validates teacher/student links on every build: it flips a teacher born after the student, downgrades pairs whose lifetimes can't overlap to `influence`, and drops non-person ends and contradictory pairs. The rules are in the comment block above `TS = ('teacher', 'student')`. Every change goes to `data/link_validation_report.txt` for human review; don't edit that report by hand. `influence` means **source influenced target**. Most influence links come from the spreadsheet's "דמויות/השפעות קשורות" column, which lists predecessors and successors alike, so the rebuild orients each one earlier → later, and resolves its names with `find_related`: whole-word matching, no bare given names inside longer phrases ("ספר שמואל" is not שמואל האמורא), and era-checked disambiguation. `find_node`'s looser matching is kept for the curated-link recovery, which was calibrated against it.
- **Region keys**: `ashkenaz, east-europe, tsarfat, provence, sefarad, italy, north-africa, mizrach, eretz-israel, other` — derived from free-text `location` via `lib/regions.ts::regionsOf` (keyword matching), not stored directly on most sages. A keyword counts only **as a word**: at the start of the text, after a separator or after a one- or two-letter Hebrew prefix (ב ל מ ש ה ו כ); a keyword of three letters or fewer must also end the word (`לוב`, `פס`, `עכו` are whole names), a longer one may take a suffix because many are stems on purpose (`בוהמי`, `אלג`, `קסטילי`). It used to match anywhere, so Libya was found inside שקלוב (Shklov), לובלין (Lublin), שידלוב and מיקולוב, and `רוסיה` inside פרוסיה; on 2026-10-18 six sages' regions changed, all corrections (117, 527, 540 and the Lublin stops of 70, 76, 488 were filed under North Africa), and `פרוסיה` and `שקלוב` were added as East European keywords so that 105, 528, 546 and 540 keep a region. No coordinate changed. `tests/geoLayers.test.ts` pins it.
- **Map coordinates** come from one resolver, `lib/locationCoords.ts` (`resolveCoords` / `primaryPlaceOf`), shared by the map markers and the place cohorts. It uses whole-word matching and prefers city over region over country; when a sage has several places at the same level, it takes the one mentioned first. Explicit `lat`/`lng` on a sage wins. Don't add a second place lookup; extend the gazetteer in that file instead.
- Hebrew is written with proper גרשיים (e.g. `רמב״ם`, not `רמבם`), and RTL is the default direction; English/Russian content is LTR overlay only.

## Research Document Ingestion Workflow

When adding research documents from Google Drive to existing sages:

### Setup
1. **Manifest file**: Create or update a JSON manifest at `/tmp/claude-0/-home-user/4ee6b46b-17bb-58f3-a062-e7061ae6d87c/scratchpad/approved_46_minus_7.json` with an array of objects:
   ```json
   [
     {
       "title": "Research title",
       "sage_id": "123",
       "sage_label": "Hebrew sage name",
       "spotify": "https://open.spotify.com/episode/...",
       "drive_id": "Google Drive document ID"
     }
   ]
   ```

2. **Output format**: Each research document is written to `nextjs-app/public/research/<sage_id>.json` as:
   ```json
   [
     {
       "title": "Document title",
       "source_file": "Google Docs: [original title]",
       "word_count": 12345,
       "content": "Full text content of the document..."
     }
   ]
   ```
   If multiple documents exist for the same sage_id, they are appended to the array.

### Process
1. **Triage**: Categorize documents from Google Drive folder into matching sages vs. new candidates
2. **Filter**: Remove sages that don't exist in the data.json (validate FK constraints)
3. **Ingest**: For each approved document:
   - Download Google Doc via Drive API (requires authentication)
   - Extract text content
   - Count words
   - Write JSON file to output directory
   - Append to existing files if sage already has research
4. **Validate**: Verify all JSON files are valid and properly formatted

### Google Drive API Authentication
- Requires Google Drive connector enabled in Claude Code session
- Uses service account or OAuth credentials
- Downloads via `google.drive.files.export` (converts Google Docs to plain text)

### Common Issues
- **API Timeout**: If processing many documents, batch in groups of 10-15 to avoid timeouts
- **Missing Sage**: Validate sage_id exists in `nextjs-app/public/data.json` before ingestion
- **Duplicate Entries**: Check if research already exists for a sage_id; append rather than replace
- **Word Count**: Use simple split on whitespace; emoji/special chars may inflate count slightly

### Environment Variables (`.claude/settings.json`)
- `RESEARCH_MANIFEST_PATH`: Path to approved documents manifest
- `RESEARCH_OUTPUT_DIR`: Target directory for research JSON files (relative to repo root)
